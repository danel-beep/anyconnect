# Мессенджеры: Telegram, WhatsApp и шлюз сессий

Этот документ описывает, как хаб работает с мессенджерами: где хранятся сообщения, как они
отправляются без риска бана, что такое шлюз сессий и как добавить новый мессенджер.

## Два вида подключения

| Вид | Примеры | Где работает | Транспорт (`messenger.transport`) |
| --- | --- | --- | --- |
| Официальный API с вебхуками | Telegram Bot API (свой бот или бот хаба в «Автоматизации чатов»), WhatsApp Cloud API | В самом хабе | `{ kind: 'direct', send, webhook, … }`; у бота хаба вместо `webhook` — `routed` |
| Постоянная сессия | Telegram как личный аккаунт (MTProto), WhatsApp через официальное приложение на устройстве | Во внутреннем сервисе «шлюз» | `{ kind: 'session' }` |

ИИ не видит разницы: у любого мессенджера одинаковые инструменты (`list_chats`, `search`,
`read_chat`, `whats_new`, `send`, `mark_read`, `get_attachment`), и они же реализуют общие
интерфейсы `messages.*`, так что `messages_search` ищет сразу во всех аккаунтах Telegram,
WhatsApp и почты. Аккаунтов одного мессенджера может быть сколько угодно.

## Хранилище сообщений

Хаб хранит свою копию переписки (`messenger_chats`, `messenger_messages`). Поэтому чтение и
поиск не обращаются к мессенджеру: это быстро, не тратит лимиты и не выглядит для мессенджера
как подозрительная активность.

- **Всё зашифровано ключом аккаунта.** Текст, отправитель, вложения, название чата, задачи
  очереди и состояние сессии лежат в `*_encrypted`, зашифрованные собственным ключом данных
  аккаунта (`accounts.data_key_encrypted`, AAD = id строки; `src/messaging/ciphers.ts`). Удаление
  аккаунта удаляет и ключ вместе со строкой аккаунта. В старой резервной копии базы строка
  аккаунта с ключом (зашифрованным `ENCRYPTION_KEY`) ещё есть, поэтому переписка исчезает
  окончательно, только когда удаляются резервные копии (`BACKUP_RETENTION_DAYS`, по умолчанию 30). Ротация `ENCRYPTION_KEY` перешифровывает только сам ключ аккаунта. Записи, сделанные до
  появления ключей аккаунтов, читаются по-прежнему (через главный ключ). Внешние id (id чата и сообщения в мессенджере) хранятся только
  как ключевые HMAC-хэши, поэтому дедупликация работает, а сами id не видны.
- **Поиск по зашифрованному.** Для каждого слова хранится 32-битный HMAC-токен его начал
  (3–12 букв) с лёгким стеммингом для русского и английского. Токены лежат в `int[]` с GIN-индексом;
  запрос превращается в токены, кандидаты расшифровываются и проверяются по настоящему тексту.
  «встреч» находит «встреча» и «встречу», «счета ноябрь» находит «счёт за ноябрь».
- **Ключ данных переживает ротацию.** Ключи хэшей и поиска выводятся (HKDF) из отдельного ключа
  данных, который хранится в `data_keys` зашифрованным `ENCRYPTION_KEY`. Ротация `ENCRYPTION_KEY`
  перешифровывает только его, индексы остаются верными.
- Повторный вебхук (мессенджеры повторяют доставку) не создаёт второе сообщение; правки и
  удаления обновляют существующую строку, у удалённых стирается текст.
- `whats_new` отдаёт курсор: ИИ передаёт его в следующий раз и получает только новое.

### Ведение переписки: ИИ ждёт ответа и отвечает

Когда пользователь просит ИИ «переписываться» с кем-то (договориться с клиентом о цене, ответить
на вопросы, дождаться ответа), любому ИИ-приложению нужны две вещи: ждать нового сообщения внутри
своего хода и отправлять ответы, не спрашивая пользователя на каждое. Новых кнопок нет: ИИ узнаёт
о режиме из описаний инструментов и одной строки в инструкциях коннектора
(`conversationInstructions`), и включает его только по просьбе пользователя.

- **`wait_for_reply`** (у каждого мессенджера из `messengerActions`) ждёт до `timeout_seconds`
  (по умолчанию 45, максимум 100) и возвращается, как только в чате (или в любом чате аккаунта)
  появилось входящее сообщение: `status: new_messages` с сообщениями и курсором, `no_reply_yet`
  с тем же курсором (ИИ вызывает снова, пока не вышло время, которое дал пользователь) или
  `account_offline`, если сессия не в сети и ждать бессмысленно. Без курсора ожидание начинается
  после последнего своего сообщения в чате, поэтому ответ, пришедший до вызова, не теряется.
  Курсор тот же, что у `whats_new`, вызов без состояния: оборванный клиентом вызов ничего не
  теряет. 45 секунд выбраны под лимит вызова инструмента у Claude и ChatGPT (около 60 секунд);
  Claude Code и агенты могут ждать дольше, хаб ограничивает вызов `TOOL_TIMEOUT_SECONDS` (120).
- **Мгновенное пробуждение.** `MessageStore` после нового входящего сообщения вызывает
  `InboundSignal.notify` (`src/messaging/inbound-signal.ts`): ожидания в этом процессе будятся
  напрямую, в других (шлюз, другие инстансы) — через Postgres NOTIFY на канале
  `messenger_inbound`. Без уведомлений ожидание заглядывает в базу раз в 2 секунды. На аккаунт в
  процессе не больше 5 одновременных ожиданий.
- **Пустое ожидание не считается использованием** (`countsAsUsage`): часы ожидания не съедают
  лимит тарифа, считается только ожидание, которое принесло сообщения.
- **`start_conversation`** (`chat`, `goal`, `hours` до 72, `max_messages` до 100) — опасное
  действие: по умолчанию пользователь подтверждает его один раз (ссылкой или в чате, как
  настроено) и видит цель, срок и лимит. После этого `send` в этом чате от этого же ИИ-приложения
  идёт без подтверждения, пока не кончится срок или лимит сообщений (разовое разрешение,
  docs/ARCHITECTURE.md, «Разовые разрешения на серию вызовов»). Другие чаты, другие ИИ-приложения
  и общее подключение команды не покрываются. **`end_conversation`** заканчивает разрешение
  раньше; описание `start_conversation` велит ИИ остановиться и рассказать пользователю, когда цель
  достигнута, собеседник закончил разговор или просит то, что может решить только пользователь,
  что-то выглядит странно или время вышло.
- Ход ИИ в чат-приложениях не бесконечен: Claude и ChatGPT ведут переписку, пока открыт ответ
  (десятки минут, каждый пустой вызов стоит ИИ около сотни токенов контекста).
- **«Будильники» для долгой переписки.** Ответ `start_conversation` несёт `follow_up`: когда
  предлагать проверку по расписанию и готовый текст задачи (чат, цель, срок, правила остановки).
  Если приложение умеет ставить себе задачи (запланированные задачи Claude и ChatGPT — не чаще раза в
  час и на платных тарифах; Claude Code — `/loop` и cron, хоть каждую минуту), ИИ предлагает
  пользователю такую проверку и ставит её только с его согласия. Хаб не знает, какой планировщик у
  клиента, поэтому подсказка общая. Запуск по расписанию идёт через то же ИИ-приложение, так что
  разрешение переписки на него действует; `wait_for_reply` без курсора начинает после своего
  последнего сообщения, поэтому задаче не нужно хранить состояние. Пустая проверка не тратит лимит
  тарифа. Автономный режим на стороне хаба (свой LLM отвечает, пока пользователь не в чате) —
  следующий шаг; он требует платного LLM и решения владельца.

### Сроки хранения

Это обещано пользователям в политике конфиденциальности (`src/web/legal.ts`, раздел о сроках
хранения): меняя сроки здесь, поправьте и её.

- **Переписка** (`messenger_chats`, `messenger_messages`) хранится столько, сколько выбрано на
  странице аккаунта («Хранить сообщения в Manyplug»): 30, 90 или 365 дней либо пока аккаунт
  подключён. Срок лежит в `accounts.settings.keepMessagesDays` (нет значения = пока подключён).
  Новый аккаунт мессенджера получает 90 дней (`DEFAULT_MESSAGE_RETENTION_DAYS` в
  `core/accounts.ts`); аккаунты, подключённые до появления настройки, хранят всё, пока владелец
  сам не выберет срок. Сообщения старше срока раз в сутки удаляет задача
  `messaging.prune_messages` (`MessageStore.prune`, пачками по 5000), а при приёме истории
  (`ingest`) такие сообщения не записываются заново. Чаты остаются в списке. Удалённые в
  мессенджере сообщения теряют текст и вложения.
- **Очередь отправки** (`messenger_outbox`): завершённые задачи (`sent`, `failed`, `uncertain`,
  `cancelled`) удаляет задача `messaging.prune_outbox` раз в сутки, через
  `OUTBOX_RETENTION_DAYS` (30) дней после завершения.
- **Отключение аккаунта** удаляет строку `accounts`, а с ней каскадом чаты, сообщения, очередь,
  `messenger_state` и `messenger_accounts`.
- Регулярные задачи подсистемы объявлены в `Messaging.jobs` (`src/messaging/index.ts`) и
  регистрируются хабом вместе со встроенными.

## Отправка: очередь, темп, ровно один раз

`send` не отправляет сообщение сам, а ставит задачу в `messenger_outbox` и ждёт до 12 секунд.
Ответ — `sent`, `queued` (с `eta`, если, например, сработал лимит) или `uncertain`.

- **Прочитано — только когда ИИ отвечает.** Если в чате есть непрочитанные входящие, `send`
  сначала ставит в очередь `mark_read` до последнего входящего, а потом само сообщение: собеседник
  видит, что его сообщение прочитали, и только потом ответ, как у человека. Чтение (`read_chat`,
  `search`, `whats_new`, `wait_for_reply`) ничего не отмечает: непрочитанное остаётся
  непрочитанным у пользователя, пока ИИ не написал в этот чат (так попросил владелец). Явная
  отметка без ответа — `mark_read`. Где мессенджер не знает «прочитано» (обычный чат бота), задача
  ничего не отправляет.
- **Без дублей.** Одинаковый запрос (тот же чат, тот же текст, тот же ответ на сообщение) в
  течение 10 минут сливается с первым (`deduplicated: true`), даже если ИИ повторил вызов, пока
  первый ещё отправлялся. Поверх этого работает общая защита хаба от повторов записи.
- **По одной задаче на аккаунт.** Задачи берутся `FOR UPDATE SKIP LOCKED`, порядок сохраняется,
  несколько процессов хаба и шлюза могут работать одновременно.
- **Без опроса базы.** Диспетчер (`src/messaging/dispatcher.ts`) не заглядывает в очередь каждую
  секунду. Новая задача будит его сразу: в своём процессе вызовом `kick()`, в других процессах
  через Postgres NOTIFY на канале `messenger_outbox` (одно слушающее соединение на процесс,
  `src/db/listener.ts`). Задача, отложенная темпом или лимитом, будит его к своему `not_before`;
  задачу, которую сейчас отправляет другой процесс, он проверяет раз в секунду, пока она не уйдёт.
  В простое — один взгляд в минуту на всякий случай. Пока соединение для уведомлений не работает,
  диспетчер опрашивает очередь раз в секунду, как раньше, а после восстановления перечитывает её.
  Соединение раз в минуту проверяет, что всё ещё слушает свои каналы (за пулером в режиме
  транзакций LISTEN молча не работает), и иначе переподключается.
- **Снятие паузы** (`POST /api/v1/accounts/<id>/messenger/resume-sending`) сразу освобождает
  задачи, отложенные до конца паузы, и будит диспетчеры всех процессов.
- **Темп «как человек»** (`src/messaging/pacing.ts`): случайная пауза между сообщениями,
  лимиты в минуту/час/сутки, отдельный лимит первых сообщений новым людям в сутки,
  «печатает…» перед отправкой (35–60 мс на символ, 1–8 секунд). Значения по умолчанию задаёт
  коннектор (`messenger.pacing`), пользователь может переопределить их в настройках аккаунта
  (`pacing`).
- **Ошибки доставки** (`DeliveryError`):
  - `rate_limited`: аккаунт ждёт сколько сказал мессенджер; ожидание дольше 5 минут ставит
    отправку на паузу и показывается пользователю.
  - `spam_warning`: пауза на 24 часа.
  - `auth`: задача не выполнена, аккаунт помечается «нужен повторный вход».
  - `rejected`: задача не выполнена, причина возвращается ИИ.
  - `transient`: до 5 попыток с нарастающей паузой.
- **Прерванная отправка.** Если процесс упал посреди отправки, задача возвращается в очередь
  только у транспортов, которые сами отсекают дубли (`idempotentSend`). Иначе она становится
  `uncertain`: лучше честно сказать «не уверены», чем отправить человеку два одинаковых сообщения.
- **Подтверждение.** Как и отправка почты, `send` по умолчанию ждёт согласия пользователя
  (риск `dangerous`: в чате, в Telegram или на странице подтверждений). Правило «не спрашивать»
  для сервиса или аккаунта это снимает, но первое сообщение новому человеку, самое рискованное
  действие для бана, `assessRisk` всё равно помечает отдельно, с причиной.
- **Чужой текст — это данные.** Результаты всех инструментов мессенджеров (даже тех, что читают
  копию в хабе) хаб помечает как сторонний контент `⟦untrusted⟧`, чтобы ИИ не выполнял
  инструкции из чужих сообщений.

**Файлы.** `send` принимает `file_url` — публичную https-ссылку на файл. Вид файла (фото,
видео, аудио, документ) определяется по расширению или задаётся `file_kind`; фото — только
JPG/PNG, видео — MP4/3GP, остальное уходит документом. `text` становится подписью (до 1024
символов), `file_name` — именем файла у получателя.

- WhatsApp и Telegram в большинстве случаев скачивают файл по ссылке сами.
- Telegram по ссылке принимает не всё: документы только PDF/ZIP/GIF, аудио MP3/M4A, видео MP4,
  OGG/OPUS уходят голосовым. Остальное, а также файлы со своим именем, хаб сам скачивает (не
  больше 20 МБ, через сетевую политику хаба, без доступа к внутренним адресам) и загружает в
  Telegram. Отправленный файл Telegram возвращает, так что `get_attachment` потом скачивает его
  как полученный.
- Для файла, отправленного по ссылке без копии, `get_attachment` возвращает исходную ссылку.

Транспорт объявляет поддержку флагом `files: true`, а виды файлов без подписи — в `captionless`.
У WhatsApp это аудио: такая отправка с текстом отклоняется сразу, до очереди. WhatsApp скачивает
файл уже после того, как принял сообщение, поэтому `sent` означает, что Meta приняла сообщение.
Если файл не скачался, это видно в статусе доставки (ниже).

**Статусы доставки.** WhatsApp присылает статусы своих сообщений: отправлено, доставлено,
прочитано, не доставлено (с причиной). Вебхук передаёт их через `hook.delivery(...)`, хранилище
(`MessageStore.recordDelivery`) двигает статус только вперёд и под блокировкой строки, так как
статусы приходят не по порядку и одновременно. Ошибка доставки окончательна. Инструменты
чтения показывают у своих сообщений `delivery` и `delivery_error`, так что ИИ видит, что
сообщение не дошло. Статус, пришедший раньше, чем сообщение записалось в хранилище, теряется, но
следующий статус это исправит. Драйверам шлюза этот вызов пока не передаётся.

Пауза отправки снимается в API: `POST /api/v1/accounts/:id/messenger/resume-sending`.
Состояние аккаунта: `GET /api/v1/accounts/:id/messenger`.

## Официальные API

### Telegram Bot API (`telegram_bot`)

Telegram — два отдельных сервиса (с ноября 2026): `telegram` — личный аккаунт (сессия в шлюзе,
раздел ниже), `telegram_bot` — бот через Bot API. Инструменты бота называются
`telegram_bot_list_chats`, `telegram_bot_send` и т. д. Раньше это был один сервис с полем `mode`;
миграция `0024_telegram_split` перенесла ботов в `telegram_bot` вместе с их правилами.

Токен бота от @BotFather. При добавлении аккаунта хаб вызывает `getMe` и регистрирует вебхук
`/hooks/messenger/<id аккаунта>` с секретом (заголовок `X-Telegram-Bot-Api-Secret-Token`).
Адрес публичный, поэтому всё, что не похоже на id аккаунта или не нашлось в базе, получает 404 до
любых счётчиков: лимит запросов (600 в минуту) считается только для существующих аккаунтов, и
выдуманные id не могут вытеснить из памяти счётчики, которые защищают вход.
Бот не может первым написать человеку, поэтому `send` работает только в существующие чаты.

**Telegram Business.** Любой пользователь Telegram (с мая 2026 года Premium не нужен) может
подключить того же бота к своему личному аккаунту в «Настройки → Автоматизация чатов» (раньше
«Telegram для бизнеса → Чат-боты»). Тогда бот получает его личные
переписки (`business_message`, правки, удаления), и они появляются в хабе как обычные чаты
этого аккаунта: входящие от собеседника, исходящие от владельца с телефона или от бота. Ответы
уходят через `business_connection_id`, от имени пользователя, а `mark_read` ставит отметку
«прочитано» (`readBusinessMessage`, если у бота есть это право). Внешний id такого чата —
`<id чата>@<id подключения>`. После переподключения бота появятся новые чаты, старые
останутся для чтения. Это официальный способ дать ИИ личные чаты Telegram без MTProto и без
риска для аккаунта, но только личные (не группы). Без своего бота то же самое даёт бот хаба
(следующий раздел).

### Бот хаба в «Автоматизации чатов» (`telegram_bot`, `bot: hub`)

Самый быстрый способ дать ИИ личные чаты Telegram, меньше минуты: человек сканирует QR-код на
сайте, вводит на той же странице код из бота хаба и добавляет этого бота в «Настройки →
Автоматизация чатов». Ни пароля, ни своего бота.

- **Где начинается.** `/connect/telegram_bot` (сервис «Telegram Bot») открывает не форму, а
  страницу с QR-кодом (`/connect/telegram/link/<id>`), если у хаба есть бот
  (`TELEGRAM_BOT_TOKEN`) с включённым режимом Business (`getMe` → `can_connect_to_business`).
  Туда же ведёт `/connect/telegram`, пока личный аккаунт на сервере недоступен (нет
  `TELEGRAM_API_ID`): страница «недоступно» предлагает Telegram Bot. Иначе, а также по
  `?via=form` и по ссылке внизу страницы, открывается обычная форма с токеном своего бота. Поле
  `bot` в форме не показывается (`ui.formHiddenOptions` скрывает `hub`, а поле с единственным
  оставшимся значением форма не выводит), такой аккаунт создаёт только бот хаба. Это общий шов
  `QuickConnects` (`src/core/quick-connect.ts`): поток быстрого подключения объявляет, доступен
  ли он сейчас и какие аккаунты переподключает; `connect_account` в чате тогда отвечает
  `method: 'app'`. Создание ссылок ограничено 30 в час на пользователя.
- **Ссылка.** В QR-коде `t.me/<бот>?start=c_<код>`. Код одноразовый и живёт 15 минут; в базе
  `telegram_links` лежат его хеш и зашифрованная копия для показа QR (SecretBox, AAD = id ссылки).
  Ссылку забирает первый открывший её аккаунт Telegram, остальным бот отвечает, что ссылка чужая.
  Новая ссылка отменяет прежние незавершённые ссылки того же пользователя.
- **Код из бота.** Бот показывает замаскированную почту владельца (`d•••@gmail.com`) и команду и
  присылает код из 6 цифр, который вводят на странице ссылки. Ввести его может только тот, кто
  создал ссылку и вошёл на сайт, поэтому подключение доказывает, что Telegram и сессия на сайте у
  одного человека: чужой QR-код (присланный мошенником) не подключит и не перенесёт переписку,
  пока человек сам не отдаст код, а бот прямо просит никому его не отправлять. Кнопки
  «Подключить» в боте нет, только «Отмена». Код выводится ключом хаба из id ссылки и аккаунта
  Telegram, поэтому при повторном сканировании он тот же; в базе только его хеш, после 5 неверных
  попыток ссылка перестаёт работать. Если этот
  Telegram уже подключён в другом пространстве, бот предупреждает о переносе.
- **Последний шаг.** После верного кода есть 30 минут, чтобы добавить бота. Порядок не важен: если
  бот уже добавлен, аккаунт создаётся сразу. Новая ссылка отменяет только неподтверждённые
  прежние: подтверждённая ждёт Telegram, даже если страницу открыли заново. Страница сама следит за состоянием (`data-poll`:
  `GET …/state` раз в 2,5 секунды, пока вкладка открыта) и перезагружается при изменении; без
  JavaScript есть кнопка «Проверить сейчас».
- **Хранение.** Подключение Telegram присылает обновлением `business_connection`. Таблица
  `telegram_connections` хранит его только под ключевыми хешами (`telegram/user`,
  `telegram/connection`), id подключения, чат и имя зашифрованы (SecretBox, AAD = хеш
  пользователя); права — открытый список названий разрешений (`can_reply`…), о человеке они
  ничего не говорят. У ссылки чат и имя открывшего тоже зашифрованы (AAD = id ссылки). Аккаунт
  хаба — обычный `telegram_bot` с `bot: hub` и без токена; в `metadata.telegramUserKey`
  записан хеш его аккаунта Telegram. Поэтому повторное подключение того же Telegram в том же
  пространстве (и после «Отключить») возвращает прежний аккаунт, а ссылку переподключения
  (`?account=<id>`) другой аккаунт Telegram открыть не может: переписка двух людей не смешается
  в одном аккаунте.
- **Входящие.** Все обновления бота приходят на `/telegram/webhook`. Обработчики стоят цепочкой
  (`chainUpdateHandlers`): сначала `TelegramAutomation.handleUpdate` (подключения, `/start c_…`,
  `/start bizChat…`, кнопки), затем подтверждения. `business_message`, правки и удаления хаб
  отдаёт аккаунту по хешу `business_connection_id` (`MessagingService.route` → `routed`
  транспорта), обновления неизвестных подключений отбрасывает. Если сохранить не удалось,
  обработчик бросает `RetryUpdateError`, вебхук отвечает 500, и Telegram повторяет обновление
  (приём идемпотентен). Так же повторяется несохранённый `business_connection`: без него все
  сообщения подключения терялись бы. Одно обновление просит повтор не больше 3 раз
  (`RetryBudget`), чтобы ошибка, которая повторяется, не держала вебхук бота для всех.
- **Отправка.** Транспорт коннектора не знает токена бота: он зовёт порт `TelegramHubBot`, а хаб
  сам добавляет `business_connection_id` и пропускает только разрешённые методы (`sendMessage`,
  `sendPhoto`, `sendDocument`, `sendVideo`, `sendAudio`, `sendVoice`, `sendChatAction`,
  `readBusinessMessage`; `getFile` — только для скачивания файлов). Ответ 401/404 — проблема бота
  хаба: он идёт в журнал ошибок и повторяется, аккаунт переподключать не нужно. Бот общий (около
  30 сообщений в секунду на всех), поэтому темп у таких аккаунтов ниже, чем у своего бота:
  20 в минуту, 300 в час, 2000 в сутки.
- **Ограничения Telegram.** Бот видит только выбранные человеком личные чаты и только с момента
  подключения (старых сообщений нет). Отвечать он может там, где собеседник писал за последние
  24 часа, и только с правом «Отвечать на сообщения». Группы и каналы — только через личный
  аккаунт (сервис `telegram`).
- **Состояния.** Бот выключен в «Автоматизации чатов» → аккаунт `needs_reauth` (на паузе),
  включён снова → активен; если в это время была подтверждена новая ссылка, подключение уходит
  по ней. Кнопка «Отключить» в боте (`/start bizChat…` из меню «Управлять
  ботом») отвязывает аккаунт. Подключение того же Telegram к другому аккаунту переводит прежний в
  `needs_reauth`. Просроченные ссылки удаляет ночная уборка через сутки.

Владельцу хаба: в @BotFather включить у бота **Bot Settings → Business Mode**. Пока режим
выключен, сайт показывает обычную форму. Новых переменных окружения нет.

### WhatsApp Cloud API (`whatsapp`, `mode: cloud`)

Нужны `phoneNumberId`, `wabaId`, постоянный `accessToken` и `appSecret` приложения Meta. Хаб
сам подписывает вебхук на свой адрес (`override_callback_uri`), проверяет подпись
`X-Hub-Signature-256` и отвечает на проверку `hub.challenge`. Вне 24-часового окна WhatsApp
принимает только шаблоны: обычная отправка вернёт понятную ошибку `rejected`.

**Шаблоны.** `whatsapp_list_templates` показывает одобренные шаблоны номера с переменными
(нужен `wabaId`), `whatsapp_send_template` отправляет шаблон в чат или на номер. Это единственный
способ написать первым или после 24 часов. Шаблон идёт через ту же очередь, что и `send` (темп,
лимиты, без дублей, подтверждение), а в копию переписки попадает подставленный текст, так что
чат читается как обычно. Поддерживаются переменные тела, позиционные (`{{1}}`) и именованные
(`{{name}}`). Шаблоны с картинкой в заголовке или переменными в заголовке и кнопках пока не
отправляются, и `list_templates` об этом пишет. В общем ядре шаблон — это `OutboundJob.template`,
а транспорт объявляет поддержку флагом `templates: true`. Остальным транспортам `send` с шаблоном
откажет.

Секрет вебхука выводится из ключа хаба отдельно для каждого аккаунта, его не нужно хранить.

## Telegram как личный аккаунт (`telegram`)

Протокол MTProto, тот же, что у официальных приложений Telegram, через библиотеку mtcute
(`@mtcute/core`). Сессия живёт в шлюзе, драйвер — `src/gateway/drivers/telegram/`. Аккаунт видит
все чаты, группы и каналы, сообщения уходят от имени владельца. В Telegram сессия видна в
Настройки → Устройства как «Manyplug», там её можно завершить в любой момент.

**Как подключает пользователь.** На сайте: Сервисы → Telegram (ссылка `/connect/telegram`).
В форме ничего вводить не нужно. После «Подключить» форма
ведёт на страницу входа `/connect/messenger/<id аккаунта>`: QR-код (сканируется в Telegram:
Настройки → Устройства → Подключить устройство) или номер телефона и код из Telegram, затем
облачный пароль, если он включён. Код и пароль вводятся только на этой странице, хаб передаёт их
шлюзу и нигде не хранит, в логи они не попадают. Страница QR перезагружается сама каждые
3 секунды, без скриптов. Пока вход не завершён, аккаунт в статусе `needs_reauth`, и ИИ видит
причину.

**Ключи приложения.** Для MTProto нужно приложение Telegram: `api_id` и `api_hash` с
my.telegram.org → API development tools. Это ключи самого Manyplug, одни на все аккаунты, они
задаются на шлюзе (`TELEGRAM_API_ID`, `TELEGRAM_API_HASH`). Пользователям их вводить не нужно.
Без них драйвер сообщает, чего не хватает (`SessionDriver.missing`, `GET /v1/drivers` шлюза), и
хаб не даёт начать подключение: каталог показывает Telegram как «ждёт настройки», страница
`/connect/telegram` объясняет причину и предлагает Telegram Bot, а админка («Система» → «Личные
аккаунты Telegram») называет переменные. Проверка — `SessionAvailability` в `src/messaging/`
(через шов `ConnectorAvailability` в `WorkspaceAdmin`), ответ шлюза кэшируется на 30 секунд.

**Хранение.** Состояние mtcute (ключи авторизации, состояние обновлений, кэш собеседников с
access hash) лежит в `messenger_state`, зашифрованное ключом аккаунта. Ключи авторизации
пишутся сразу, остальное пачкой через ~2 секунды после того, как mtcute просит сохранить, и при
остановке. Кэш собеседников разбит на 64 строки по `|id| mod 64`, так что новый контакт
переписывает одну небольшую строку, а id из Telegram не попадают в названия ключей.

**Что умеет.** Список чатов с непрочитанными (счётчик Telegram, а не наш подсчёт), история
(после первого входа — последние 20 сообщений 40 верхних чатов, дальше `backfill` по запросу),
новые сообщения и правки в реальном времени, пропущенное за время простоя (`getDifference`
при подключении), прочтение на телефоне обнуляет счётчик, отправка текста с ответом на
сообщение, `mark_read`, поиск собеседника по @username или id, скачивание вложений (до 50 МБ,
сообщение перечитывается ради свежей ссылки на файл). Отправка идёт с `random_id` из id задачи,
поэтому повтор после сбоя не создаёт дубль (`idempotentSend: true`). Темп отправки человеческий
(значения хаба по умолчанию). Пока нет: отправки файлов (`send` с файлом откажет до постановки в
очередь), удалений сообщений в личных чатах.

**Ошибки.** `FLOOD_WAIT` → `rate_limited` с паузой, `PEER_FLOOD` → `spam_warning` (отправка
ставится на паузу), `AUTH_KEY_UNREGISTERED`/`SESSION_REVOKED` → сессия `logged_out` (нужно войти
заново), `USER_DEACTIVATED*` → `banned`, `FROZEN_*` → `frozen`. Раз в 4 минуты сторож вызывает
`updates.getState`: так шлюз замечает завершённую с телефона сессию. Сетевые сбои mtcute
переживает сам, сессия считается потерянной после трёх неудачных проверок подряд.

**Риск для аккаунта.** Telegram разрешает сторонние клиенты, но блокирует за спам и массовые
рассылки. Поэтому человеческий темп, лимит новых собеседников в день и подтверждение отправки
остаются включёнными.

**Тесты.** `test/fake-telegram.ts` — поддельный клиент mtcute с настоящими объектами `Message`
и `User`; `test/telegram-user.test.ts` (хранилище, разбор, ошибки, вход по QR и по коду),
`test/telegram-login.e2e.test.ts` (форма на сайте → вход с паролем → чаты → отправка через ИИ).

## Шлюз сессий

Постоянные соединения (личный Telegram, WhatsApp) держит отдельный процесс:
`node dist/gateway/index.js` (тот же образ, что и хаб). Это внутренний сервис без публичного
адреса; хаб обращается к нему по `GATEWAY_URL` с общим секретом `GATEWAY_TOKEN`. Оба процесса
используют одну базу и один `ENCRYPTION_KEY`. Шлюз доверяет хабу, поэтому права проверяет хаб: id
аккаунта он берёт из своей базы после проверки владельца, id входа со страницы принимает только в
виде `lgn_…`, а клиент шлюза (`HttpGatewayClient`) кодирует каждый id как один сегмент пути, так
что `../` в адресе страницы не приводит к методу чужого аккаунта.

```
ИИ ──MCP──▶ хаб ──(чтение, поиск, очередь)──▶ Postgres ◀── шлюз ◀──▶ мессенджер
              └──── вход, файлы, история ──HTTP──▶ шлюз
```

Почти всё идёт через базу: шлюз пишет входящие сообщения в хранилище и забирает задачи из
очереди. По HTTP хаб зовёт шлюз только для того, что требует живого соединения: вход (QR, код,
пароль 2FA), поиск получателя по номеру или @username, скачивание файла, загрузка старой
истории.

### Одна сессия на аккаунт

Две живые копии одной сессии — главная причина конфликтов ключей и принудительного выхода.
Поэтому сессией владеет аренда (`messenger_accounts`): владелец, срок и fencing-токен, который
растёт с каждой новой арендой.

- Экземпляр шлюза продлевает аренду каждую треть срока. Если продлить не удалось, сессия
  останавливается сразу, не дожидаясь конца срока.
- Состояние сессии (`messenger_state`, зашифровано) записывается только вместе с проверкой, что
  аренда с этим токеном всё ещё наша (`FencedSessionState`). Старый владелец после разрыва сети
  ничего не может перезаписать.
- При штатной остановке (деплой) аренды освобождаются, и другой экземпляр подхватывает аккаунты
  сразу. Запросы хаба идут на тот экземпляр, который держит аренду (`lease_owner_url`).

### Переподключение и предохранитель

- Старт сессий размазан случайной задержкой, чтобы после рестарта все аккаунты не подключались
  одновременно.
- Временные сбои (`network`, `protocol`, `phone_offline`, `flood`) дают паузу
  `база × 2^n` со случайным разбросом, до 15 минут.
- После 8 сбоев подряд аккаунт останавливается (`failing`), пока пользователь не вмешается.
- Фатальные проблемы останавливают аккаунт сразу и показываются пользователю и ИИ в статусе
  аккаунта: `logged_out` (вышли на телефоне), `needs_password` (нужен пароль 2FA), `frozen`
  (мессенджер ограничил аккаунт), `banned`.

### Драйверы

Протокол конкретного мессенджера — это драйвер (`src/gateway/drivers/types.ts`):

```ts
interface SessionDriver {
  connectorId: string;                       // какой коннектор с transport 'session' он обслуживает
  connect(session): Promise<LiveSession>;    // подключиться с сохранённым состоянием
  login?(session, input): Promise<LoginFlow>; // интерактивный вход
}
```

Драйвер получает зашифрованное хранилище состояния, функции для записи сообщений и чатов,
сигнал остановки и сетевую политику хаба. Всё остальное (аренды, очередь, темп, статусы,
переподключение) делает шлюз. `LiveSession.closed` завершается ошибкой `SessionError` с
классом проблемы, и по нему шлюз решает, переподключаться или остановить аккаунт.

Сюда же встраиваются будущие транспорты WhatsApp через официальное приложение: агент на
устройстве (свой телефон, облачный Android или выделенное железо) подключается к шлюзу
исходящим соединением, а для шлюза это обычный драйвер с той же аренды, очередью и статусами.

### Шлюз внутри хаба (`GATEWAY_EMBEDDED=true`)

Пока аккаунтов мало, шлюз можно не выносить в отдельный сервис: с `GATEWAY_EMBEDDED=true` хаб
сам запускает ту же среду шлюза и его внутренний API на `127.0.0.1:10001`
(`GATEWAY_EMBEDDED_PORT`) со случайным токеном, придуманным при старте, и обращается к нему как
к обычному шлюзу (`src/gateway/embedded.ts`). `GATEWAY_URL` и `GATEWAY_TOKEN` при этом не
задаются, а `TELEGRAM_API_ID`/`TELEGRAM_API_HASH` ставятся на сам хаб. Цена: сессии
переподключаются при каждом деплое хаба и делят с ним память. Во время деплоя старый экземпляр
держит аренды, пока не получит SIGTERM, так что двух копий одной сессии не бывает.

Переход на отдельный шлюз — только настройки: убрать `GATEWAY_EMBEDDED`, поднять сервис
`node dist/gateway/index.js` с теми же `DATABASE_URL`/`ENCRYPTION_KEY` и задать хабу
`GATEWAY_URL` (можно `host:port` из приватной сети Render) и `GATEWAY_TOKEN`. Сессии продолжатся
с сохранённым состоянием. Сейчас (ноябрь 2026) на проде шлюз встроенный: отдельный платный
сервис отложен до первых пользователей.

### Ресурсы

Одна сессия MTProto или WhatsApp занимает примерно 10–40 МБ памяти. `GATEWAY_MAX_SESSIONS`
(по умолчанию 200) ограничивает число сессий на экземпляр; при росте добавляются экземпляры
шлюза, аренды распределяют аккаунты между ними сами.

## Переменные окружения

| Переменная | Где | Назначение |
| --- | --- | --- |
| `GATEWAY_EMBEDDED` | хаб | `true` — шлюз в процессе хаба (см. выше); исключает `GATEWAY_URL`. `GATEWAY_EMBEDDED_PORT` — его порт на localhost (10001). |
| `GATEWAY_URL` | хаб | Внутренний адрес шлюза, например `http://anyconnect-gateway:10000`. Без него аккаунты с постоянной сессией не работают, официальные API работают. |
| `GATEWAY_TOKEN` | хаб и шлюз | Общий секрет, не короче 32 символов. |
| `GATEWAY_ADVERTISE_URL` | шлюз | Адрес этого экземпляра для хаба (по умолчанию `http://<hostname>:<PORT>`). |
| `GATEWAY_MAX_SESSIONS` | шлюз | Предел сессий на экземпляр. |
| `DATABASE_URL`, `ENCRYPTION_KEY` | шлюз | Те же, что у хаба. |
| `TELEGRAM_BOT_TOKEN` | хаб | Бот хаба: подтверждения и подключение личных чатов через «Автоматизацию чатов» (`telegram_bot` с `bot: hub`, нужен Business Mode в @BotFather). |
| `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` | шлюз (со встроенным шлюзом — хаб) | Приложение Telegram с my.telegram.org для личных аккаунтов (задаются вместе, hash — 32 символа). |

## Как добавить мессенджер

1. Коннектор в `src/connectors/builtin/` с полем `messenger`:
   - для официального API — `transport: () => ({ kind: 'direct', idempotentSend, send, webhook, download, resolveRecipient })`;
   - для постоянной сессии — `transport: () => ({ kind: 'session' })` и драйвер в `src/gateway/drivers/`.
2. Инструменты: `actions: (action) => messengerActions(action, deps.messaging, { serviceName })`.
   Свои дополнительные действия можно добавить к этому списку.
3. Ошибки отправки — `DeliveryError` с правильным видом (`rate_limited` с `retryAfterSeconds`,
   `auth`, `rejected`, `spam_warning`, `transient`). Сетевые ошибки до отправки запроса
   (`deliveryFetch`) — `transient`, остальные считаются неизвестным исходом.
4. Тесты: поддельный API на локальном Hono-сервере (`test/messengers.test.ts`) или поддельный
   драйвер (`test/fake-messenger.ts`, `test/gateway.test.ts`).
