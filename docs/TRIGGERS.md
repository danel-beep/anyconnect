# Триггеры и свой ИИ по API

Триггер — правило «когда новое сообщение или письмо подходит под фильтр, сделать …». Код в
`src/triggers/`, инструменты чата в `src/hub/trigger-tools.ts`, страницы `/app/triggers` и
`/app/ai` в `src/web/triggers.tsx` и `src/routes/triggers.tsx`.

## Зачем

ИИ-приложения (Claude, ChatGPT) действуют только по запросу. Задача по расписанию «проверяй почту
каждый час» каждый раз перечитывает всё и тратит токены. Триггер переносит слежение в хаб:
хаб и так синхронизирует мессенджеры и умеет читать почту, а ИИ включается, только когда есть
совпадение.

## Из чего состоит

| Часть | Файл | Что делает |
| --- | --- | --- |
| Определение | `triggers/spec.ts` | Фильтр (`from`, `chat`, `subject`, `text`; варианты через запятую, регистр не важен) и действие: `check`, `notify`, `tool`, `ai`. Лимиты по умолчанию |
| Сопоставление | `triggers/match.ts` | Чистые функции: подходит ли событие, подстановка `{{from}}`, `{{text}}`… в аргументы |
| Источники событий | `triggers/sources.ts` | `EventSource`: `MessageSource` (хранилище сообщений мессенджеров, `whatsNew` по курсору) и `MailSource` (любой коннектор с возможностью `mail.search`) |
| Движок | `triggers/engine.ts` | Читает источники, применяет лимиты и защиту от циклов, записывает события, запускает действия |
| Хранилище | `triggers/store.ts` | Таблицы `triggers`, `trigger_cursors`, `trigger_events` |
| Ключи ИИ | `triggers/ai-keys.ts` | Таблица `ai_keys`: ключи пользователя к OpenAI, Anthropic, OpenRouter |
| Провайдеры | `triggers/ai/providers.ts` | Один шаг диалога для каждого API; новый провайдер — ещё одна запись в `AI_PROVIDERS` |
| Агент | `triggers/ai/agent.ts` | Короткий цикл «ИИ → инструменты → ИИ» для действия `ai` |
| Сервис | `triggers/service.ts` | Создание и изменение триггеров (общие правила для чата и кабинета), проверка `check` |

## Действия

- **`check`** — совпадение ждёт в хабе со статусом `new`. Задача по расписанию в ИИ-приложении
  вызывает `manyplug_check_triggers`: получает новые события (каждое один раз, затем `delivered`)
  или `{"new":0}`. Почту такая проверка читает прямо в запросе — там открыт сейф владельца,
  так что работают и запечатанные аккаунты. `create_trigger` возвращает готовый текст задачи
  по расписанию (`schedule`). Поле `task` — что сделать с совпадением, оно приходит с каждым событием.
- **`notify`** — уведомление владельцу в Telegram (`OwnerNotifier`, вид `trigger_fired`), без ИИ.
- **`tool`** — хаб вызывает один инструмент каталога с заданными аргументами (с подстановками).
  Без подтверждения, поэтому создание такого триггера из чата само ждёт подтверждения пользователя.
- **`ai`** — хаб будит ИИ ключом пользователя: событие + инструкция пользователя + только
  перечисленные инструменты (`tools`, до 20). Итог хранится в событии и по желанию приходит
  в Telegram.

## Безопасность

Все вызовы триггера идут через `Hub.callTool` и полную цепочку исполнителя под отдельным
принципалом `kind: 'automation'` (`credentialId` = id триггера, `automation` = область):

- этап **`automation`** (`hub/stages/automation.ts`, после `risk`) пропускает только инструменты
  из списка триггера, никогда не пускает инструменты настройки хаба (`scope = 'workspace'`) и, пока
  включено `askBeforeRisky`, требует подтверждения для рискованных (`dangerous`) вызовов;
- у триггеров своё ИИ-приложение в списке «ИИ-приложения» («Triggers», вид `automation`), так что
  правила доступа к аккаунтам действуют и на них; подтверждение для автоматизации никогда не
  «в чате» (чата нет), а в Telegram или на странице подтверждений;
- что важнее: настройка триггера только **добавляет** подтверждение. `askBeforeRisky: false`
  выключает подтверждение этапа `automation`, но не правила доступа: если для приложения
  «Triggers» (или для всех приложений) на аккаунте стоит «спрашивать перед рискованным»
  (по умолчанию так), отправка всё равно ждёт подтверждения. Чтобы триггер слал сам, нужно
  правило «никогда не спрашивать» для приложения «Triggers» на этом аккаунте
  (`manyplug_set_rule` с `app: "Triggers"`), а не для всех приложений; пол
  (`requiresConfirmation`, `assessRisk`) не снимается ничем;
- текст события для ИИ обёрнут в метки `⟦untrusted⟧`, системная подсказка запрещает выполнять
  инструкции из него; агент дополнительно не предлагает ИИ инструменты вне списка;
- создание и изменение триггеров `tool`/`ai` из чата, а также ослабление (`askBeforeRisky: false`,
  включение, смена фильтра у действующего триггера) ждут подтверждения пользователя (`assessRisk`);
  в команде менять триггеры могут только владелец и админы;
- ключи ИИ добавляются только на странице `/app/ai`, никогда через чат. Хранятся зашифрованными
  `SecretBox` (AAD `aikey:<id>`, мастер-ключ: ключ нужен в фоне, когда сейф закрыт), видны только
  последние 4 символа. Ключ уходит только на хост своего провайдера, через сетевую политику хаба.

Шифрование: определение триггера — `SecretBox` (AAD `trigger:<id>`); содержимое события — ключом
данных аккаунта (AAD `trigger:event:<id>`), так что удаление аккаунта уничтожает и его события;
id сообщения и собеседника хранятся только как ключевые хеши (`deriveKey('trigger-keys')`).

## Лимиты

- **Дневной лимит триггера** (`dailyRuns`, по умолчанию 200, до 100 000 или без лимита) считает все
  сработавшие события дня (UTC), включая ждущие проверки. При достижении триггер встаёт на паузу
  (`paused_reason = 'limit'`) и один раз сообщает владельцу (`trigger_paused`). Включение или новый
  лимит снимают паузу.
- **Дневной лимит ключа ИИ** — сверх него запуск пропускается (`skipped: ai_limit`), уведомление
  один раз в день.
- **Защита от циклов** — действия `notify`/`tool`/`ai` срабатывают не больше 5 раз за 10 минут на
  одного собеседника (аккаунт + чат); остальное пропускается (`skipped: loop`).
- Агент: до 6 шагов, до 4096 токенов ответа на шаг (страховка, не цель), результаты инструментов
  обрезаются до 4000 символов.

## Как события доходят

- **Сообщения**: хранилище мессенджеров шлёт `NOTIFY messenger_inbound` (из любого процесса).
  Движок слушает канал (`Triggers.start()`), ждёт чуть дольше задержки видимости хранилища
  (`VISIBILITY_LAG_MS`) и читает; уведомления за это время склеиваются в одно чтение плюс ещё один
  круг. После переподключения слушателя — полный проход.
- **Почта**: задача `triggers.scan` каждые 2 минуты опрашивает ящики (перекрытие 10 минут, страница
  20 писем; запечатанные аккаунты в фоне пропускаются), заодно подбирает сообщения, чьё
  уведомление потерялось, и помечает зависшие запуски `failed`.
- **Запуск действия**: задача `triggers.run` (`{eventId}`) в очереди; без очереди — сразу в этом
  процессе. `triggers.prune` раз в сутки удаляет события старше 30 дней.
- Курсор каждого триггера на каждом аккаунте (`trigger_cursors`) начинается с текущего конца ленты:
  триггер реагирует только на новое. Чтение одного курсора защищено advisory-блокировкой.

## Провайдеры

| Провайдер | API | Модель по умолчанию |
| --- | --- | --- |
| OpenAI | Chat Completions, `max_completion_tokens` | `gpt-5-mini` |
| Anthropic | Messages, `anthropic-version: 2023-06-01`, системная подсказка с `cache_control`, `output_config.effort: low` (только моделям, которые его принимают), содержимое ответа (включая thinking) возвращается без изменений, `stop_reason: refusal` обрабатывается | `claude-haiku-5-5` |
| OpenRouter | Совместимый с Chat Completions, заголовок `x-title` | `openai/gpt-5-mini` |

Системная подсказка одинакова на каждом пробуждении одного триггера, поэтому кешируется.

## Инструменты чата

`manyplug_check_triggers` (read), `manyplug_triggers` (read), `manyplug_create_trigger`,
`manyplug_update_trigger`, `manyplug_delete_trigger`. В списке инструментов они идут после
остальных настроечных (находятся поиском); часто используемый `check_triggers` остаётся в списке.

Ключи ИИ (`src/hub/ai-key-tools.ts`): `manyplug_ai_keys` (read: модель, лимит, запуски и токены за
сегодня, последняя ошибка, ссылка на страницу ключа), `manyplug_update_ai_key` (модель, название,
дневной лимит), `manyplug_remove_ai_key`. Сам ключ через чат не проходит никогда: его вставляют на
`/app/ai`, это единственный ручной шаг. Снижение лимита применяется сразу, повышение или снятие
ждёт подтверждения пользователя (триггеры смогут тратить больше его денег). В списке инструментов
они идут последними, чтобы не вытеснять инструменты команды. Подсказка сервера (`instructions`)
называет инструменты триггеров и ключей, чтобы ИИ сам находил их на просьбу «когда X, сделай Y».

## Страницы

Обе страницы ведут к ИИ, а не к форме. `/app/ai`: шаги «Как работает автоматизация» (вставить
ключ → сказать ИИ, что автоматизировать → дальше само), форма только из провайдера и ключа (модель
по умолчанию провайдера, 200 запусков в день), готовые фразы для ИИ; правка модели и лимита вручную
свёрнута под «Или поменяйте здесь». `/app/triggers`: «Настройте, просто попросив свой ИИ» с
фразами и четырьмя видами действий, список, живая лента; ручная форма свёрнута в «Создать
вручную».

## Известные ограничения

- Почта читается отдельно для каждого триггера на каждом ящике (общего чтения пока нет).
- Если аккаунт подключён после создания триггера, первое сообщение до появления курсора может
  быть пропущено (курсор стартует с текущего конца).
- Событие в статусе `awaiting_confirmation` не обновляется после того, как пользователь подтвердил
  действие: само действие выполняется, а лента показывает «ждёт подтверждения».
- Календарь пока не источник; подключается ещё одним `EventSource`.
- Почта опрашивается раз в 2 минуты, поэтому от письма до действия проходит 1–2 минуты (push
  Gmail через Pub/Sub пока нет). Письма в «Спаме» триггер не видит.
- Ограничить действие триггера аргументами (например, `telegram_send` только в один чат) пока
  нельзя: защита — список инструментов, правила доступа и текст инструкции.
- Подтверждение действия триггера приходит в Telegram только при подключённом боте уведомлений;
  без него оно ждёт на странице подтверждений и через 30 минут истекает, никого не известив.
