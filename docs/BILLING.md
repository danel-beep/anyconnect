# Оплата и подписки

Оплата устроена так, что платёжную систему можно поменять настройкой, не трогая остальной код.

## Как это устроено

```
кабинет /app/billing ─┐                     ┌─ PaddleProvider  (src/billing/providers/paddle.ts)
setup-инструменты ИИ ─┼─> BillingService ──>├─ StripeProvider  (…/stripe.ts)
вебхуки /billing/... ─┘   (service.ts)      └─ TestBillingProvider (…/test.ts, только разработка)
                              │
                              └─> EntitlementService.setPlan → subscriptions → лимиты, этап quota
```

- **`BillingProvider`** (`src/billing/provider.ts`) — только перевод между хабом и API провайдера:
  открыть оплату, портал, сменить цену (`changeSubscription`), отменить в конце периода,
  проверить подпись вебхука и превратить его в нормализованное `SubscriptionChange`. Поле
  `quantity` (сколько единиц цены куплено) остаётся в интерфейсе на будущее; сейчас хаб всегда
  покупает одну.
- **`BillingService`** (`src/billing/service.ts`) — всё остальное, одинаково для всех провайдеров:
  цена тарифа, покупка или смена тарифа (если подписка уже есть, второй checkout не создаётся,
  а меняется цена с пересчётом), портал, отмена, применение вебхуков. Тариф покупает только
  человек для себя: у команды своего тарифа нет (`team_no_plan`, см. «Оплата команд»). Каждое событие пишется один
  раз в `billing_events`: повторы и дубли ничего не меняют, событие старше текущего состояния
  (`subscriptions.provider_updated_at`) игнорируется, конец старой подписки не отменяет новую,
  особый тариф администратора (unlimited) провайдер не перезаписывает.
- Тариф в силе: `active`, `trialing`, `past_due` (провайдер ещё пытается списать). `paused` и
  `canceled` — бесплатный тариф. Отменённая подписка действует до конца оплаченного периода.
- Администратор не может вручную поменять тариф, который оплачивается через провайдера
  (иначе провайдер продолжит списывать деньги); добавки к лимитам работают как обычно.

## Управление через ИИ-ассистента

Setup-инструменты (`src/hub/billing-tools.ts`, реализация `src/billing/assistant.ts`):

| Инструмент | Что делает | Риск |
|---|---|---|
| `manyplug_plan` | Тариф, лимиты, расход за месяц, подписка (продление/отмена), тарифы с ценами, какие команды оплачивает тариф. В команде — кто за неё платит, каким тарифом и сколько использовано | read |
| `manyplug_buy_plan` | Ссылка на `/app/billing?plan=…&interval=…` (из команды ещё `&team=<slug>`: страница оплаты покажет путь обратно): там тариф уже выбран, пользователь подтверждает и платит | read |
| `manyplug_cancel_plan` | Отмена в конце периода (`undo: true` — вернуть) | dangerous, всегда с подтверждением |
| `manyplug_team_billing` | Только в команде: оплачивать её своим тарифом (`pay: true`), перестать (`pay: false`), режим (`mode: payer \| each`, владелец и администраторы) | write; смена режима — с подтверждением |
| `manyplug_invite` | Ссылка-приглашение пользователя и сколько людей по ней пришло | read |

Когда расход действий за месяц переходит 80% и 95% лимита, к успешному результату вызова один раз
добавляется короткая заметка для ИИ («использовано 120 из 150, сброс такого-то числа»): ассистент
упоминает её мимоходом, после задачи. Заметку добавляет этап `quota` (`QuotaDecision.notice`).

Платёж всегда проходит на защищённой странице провайдера: ИИ получает только ссылку и не может
потратить деньги сам. Тариф всегда свой: и из команды каждый участник видит, покупает и отменяет
только собственный тариф, а общий ключ команды тарифов не трогает.

## Настройки (переменные окружения)

| Переменная | Значение |
|---|---|
| `BILLING_PROVIDER` | `none` (по умолчанию: тарифы назначает администратор по запросу), `paddle`, `stripe`, `test` |
| `<PROVIDER>_PRICE_<PLAN>_<MONTH\|YEAR>` | Цена провайдера для тарифа и периода, например `PADDLE_PRICE_PRO_YEAR=pri_01…`. Тариф без цены нельзя купить; админка → Система показывает, каких цен не хватает |
| `PADDLE_API_KEY`, `PADDLE_CLIENT_TOKEN`, `PADDLE_WEBHOOK_SECRET` | Ключи Paddle |
| `PADDLE_ENVIRONMENT` | `sandbox` (по умолчанию) или `production` |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | Ключи Stripe (`sk_test_…` — тестовый режим) |

`BILLING_PROVIDER=test` — встроенный тестовый провайдер: свои страницы «оплаты» и «портала»
(`/billing/test/*`), события идут тем же путём вебхуков. Можно проверить всё без ключей. На
production запрещён (сервер не стартует).

## Paddle: подключение

1. Paddle → **Catalog → Products**: продукты Personal и Pro, у каждого две цены (месяц и год;
   суммы из `src/billing/plans.ts`: $5/$50 и $12/$120; год = два месяца в подарок). Пробный
   период в Paddle не нужен: 14 дней Pro даёт сам хаб (см. ниже). Id цен (`pri_…`) →
   `PADDLE_PRICE_PERSONAL_MONTH`, `PADDLE_PRICE_PERSONAL_YEAR`, `PADDLE_PRICE_PRO_MONTH`,
   `PADDLE_PRICE_PRO_YEAR`. Business не продаётся, отдельного командного тарифа нет (команды
   платят тарифом человека, см. «Оплата команд»), цены для них не нужны. Продукт Team из ноября
   2026 больше не нужен (его архивируют в Paddle), а `PADDLE_PRICE_TEAM_*` хаб больше не читает.
2. **Developer tools → Authentication**: API key (права на transactions, subscriptions, customers)
   → `PADDLE_API_KEY`; client-side token → `PADDLE_CLIENT_TOKEN`.
3. **Developer tools → Notifications**: адрес `https://<хаб>/billing/webhook/paddle`, события
   `subscription.*` → секрет → `PADDLE_WEBHOOK_SECRET`.
4. **Checkout → Checkout settings**: Default payment link `https://<хаб>/billing/paddle/checkout`
   (Paddle должен одобрить домен).
   Для одобрения на сайте должны быть условия (`/terms`, с разделом об оплате через Paddle как
   Merchant of Record), политика конфиденциальности (`/privacy`) и политика возврата (`/refunds`,
   14 дней на полный возврат); тексты лежат в `src/web/legal.ts`, ссылки — в подвале сайта.
   Возврат делается в Paddle (**Transactions → Refund**); подписку после возврата отменить там же.
5. `BILLING_PROVIDER=paddle`, сначала `PADDLE_ENVIRONMENT=sandbox` (отдельный аккаунт
   sandbox-vendors.paddle.com со своими ключами), после проверки — ключи боевого аккаунта и
   `production`.

Оплата открывается на странице хаба `/billing/paddle/checkout`, которая запускает Paddle.js
(у неё своя CSP с доменами Paddle, остальные страницы остаются со строгой политикой).

## Stripe: подключение

1. Products → цены для каждого тарифа и периода → `STRIPE_PRICE_<PLAN>_<MONTH|YEAR>`.
2. Developers → API keys → `STRIPE_SECRET_KEY`.
3. Developers → Webhooks: `https://<хаб>/billing/webhook/stripe`, события
   `customer.subscription.created/updated/deleted/paused/resumed` → `STRIPE_WEBHOOK_SECRET`.
4. Settings → Billing → Customer portal: включить смену карты, счета и отмену.
5. `BILLING_PROVIDER=stripe`.

## Новый провайдер

Реализовать `BillingProvider` в `src/billing/providers/<id>.ts`, добавить настройки в
`src/billing/config.ts` и ветку в `createBillingProvider` (`providers/index.ts`), тесты по образцу
`test/billing-providers.test.ts`. Остальное (кабинет, ИИ, админка, лимиты) менять не нужно.

## Старт бесплатного тарифа

Новое пространство на Free получает 14 дней Pro без карты (без облачного WhatsApp), затем
лимит действий снижается по опубликованному графику: до 30-го дня 500 в месяц, до 60-го — 300,
дальше обычные 150. Аккаунты после пробного периода — как у Free (3). График задаётся полем
`start` тарифа в `src/billing/plans.ts`, даты считает чистая функция `startSchedule`
(`src/billing/start.ts`), так что сайт, кабинет и AI (`manyplug_plan` → `start`) показывают одно
и то же. Действия, сделанные в пробный период, не списываются с первого месяца после него
(`Entitlements.countFrom`). Добавка «облачный WhatsApp» ($5 за номер) появится вместе с
мессенджерами.

Старт один на человека: он считается от создания личного пространства. Команда своего старта не
получает, она живёт на тарифе плательщика вместе с его пробным периодом, если тот ещё идёт
(`EntitlementService.planOf` даёт `start` только личным пространствам). Письмо «пробный период
заканчивается» тоже уходит только людям.

## Письма

Свои письма хаба (`src/mail/mailer.ts`, сменный `Mailer`): `MAIL_PROVIDER=none` (по умолчанию,
писем нет), `log` (разработка: в журнал пишутся только вид и тема письма), `resend`
(`RESEND_API_KEY`; отправитель `MAIL_FROM`, по умолчанию `Manyplug <hello@домен хаба>`; домен
нужно подтвердить в Resend). Новый провайдер — ещё один класс `Mailer` в `createMailer`.

`NoticeService` (`src/notices/notices.ts`) шлёт письмо владельцам пространства один раз на повод:
пара (вид, ключ) записывается в `sent_notices` до отправки, при ошибке запись снимается и повод
сработает снова. Тексты EN/RU — `src/web/i18n/email.ts`, вёрстка — `src/web/emails.ts`, язык —
`users.locale`. Поводы (`src/notices/billing-notices.ts`):

| Письмо | Когда | Ключ |
|---|---|---|
| Пробный период заканчивается | ежедневная задача `billing.trial_reminders`, за 3 дня до конца | день окончания |
| Лимит исчерпан | этап `quota` отказал в вызове | начало счёта месяца |
| Оплата не прошла | вебхук перевёл подписку в `past_due` | подписка + конец периода |
| Награда за приглашение | см. ниже | приглашённый |

Подписки на события — `EntitlementService.listen` и `BillingService.listen`; новые письма и
реакции на оплату добавляются слушателями, без кода в маршрутах.

## Приглашения

У каждого пользователя есть ссылка `/?ref=<код>` (страница тарифа и `manyplug_invite`). Код
запоминается в cookie на 30 дней (побеждает первая ссылка), при регистрации записывается в
`referrals`. Награда — когда приглашённый начинает платить (а не при регистрации: фальшивые
аккаунты ничего не дают): пригласивший на Free получает Pro на 30 дней (подписка с provider
`referral`, награды складываются), на платном Personal — лимиты Pro поверх тарифа на 30 дней
(`limit_grants`), на Pro и выше — запись `already_pro` (видна администратору, можно компенсировать
вручную). Подаренный Pro можно купить в любой момент. Код: `src/billing/referrals.ts`.

## Выручка в админке

`/admin/revenue` (`src/admin/revenue.ts`): MRR и ARR по ценам тарифов (годовые как /12), платящие
пространства, отмены в конце периода, сумма под угрозой (`past_due`), пробные и подаренные Pro,
конверсия в оплату (закончившие пробный период за 30 дней, регистрации за 30 дней, все,
приглашённые) и последние события оплаты. Считается по `subscriptions`, то есть по тому, что
провайдер прислал вебхуками; налоги и комиссия провайдера не вычитаются.

## Оплата команд

Отдельного командного тарифа нет (решение от 5 ноября 2026: тариф Team $10 за человека убран).
Тариф всегда принадлежит человеку и живёт в его личном пространстве; команда работает на тарифе
того, кто за неё платит. Как это выглядит для людей: [TEAMS.md](TEAMS.md#оплата).

- **Плательщик** — `workspaces.billing_user_id` команды; `null` — владелец. Платить может только
  участник: если плательщик вышел, снова платит владелец (`Payers.loadTeam`, а `TeamService`
  сбрасывает поле при выходе).
- **Режим** — `workspaces.billing_mode`: `payer` (один тариф на всех) или `each` (каждый
  пользуется своим). Чей тариф платит за вызов, решает одна функция `payingUser(team, userId)` в
  `src/billing/payers.ts`: в `each` — сам участник, иначе плательщик; вызов без человека (общий
  ключ, `userId = null`) и аккаунты команды — всегда плательщик.
- **Расход пишется сразу на плательщика.** Этап `meter` спрашивает `QuotaGate.payerOf` и вместе с
  обычным счётчиком (`usage_counters`, по пространству) пишет `billing_usage` (плательщик × день ×
  пространство). Лимит действий (`EntitlementService.checkAction`) сравнивает с суммой по
  плательщику: его личное пространство и все команды, за которые он платит, — один общий запас.
  Смена плательщика не переносит прошлый расход: что уже сделано, остаётся у того, кто тогда
  платил.
- **Лимит аккаунтов** считается так же (`Payers.accountsOf`): аккаунты личного пространства,
  все аккаунты команд, которые человек оплачивает целиком, а в режиме `each` — его собственные
  аккаунты в командах и аккаунты команд, за которые он платит.
- **Кто может менять** (`EntitlementService.changeTeamBilling`): взять оплату на себя может любой
  участник, если его тариф даёт команде не меньше нынешнего (`coversPlan`: действия и аккаунты,
  иначе `plan_too_small`); владелец может забрать оплату всегда. Перестать платить может только
  тот, кто платит (`not_team_payer`), и не владелец (`team_owner_pays`). Режим меняют владелец и
  администраторы (`team_admin_only`). Страница команды — `POST /app/team/<slug>/billing`
  (`pay=1|0`, `mode`), чат — `manyplug_team_billing`.
- **Размер команды** — до `MAX_TEAM_MEMBERS = 100` человек вместе с открытыми приглашениями
  (`team_full`): это защита от злоупотреблений, а не платная граница.
- **Где видно**: страница команды (блок «Кто платит»), страница «Тариф» (карточка «Ваш тариф
  оплачивает и команды», `EntitlementService.planUses`), `manyplug_plan`.
- **Админка и CLI** назначают тариф человеку: `npm run cli -- plans:set --email <почта> --plan pro
  [--days N]`; команды, которые он оплачивает, сразу работают на новом тарифе. Выручка в админке
  считается только по личным пространствам.

Почему так: людям не нужно разбираться в дополнительных тарифах, команда доступна сразу, даже на
Free, а выручка не падает: лимиты плательщика общие на всех, так что большой команде нужен
тариф побольше. Злоупотреблять неудобно: команда — один общий коннектор для людей одной
организации, каждый входит под собой.
