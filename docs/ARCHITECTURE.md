# Архитектура AnyConnect

Документ описывает фундамент (этап 1) и то, как в него встраиваются следующие этапы.

## Слои

```
src/
  connectors/   SDK коннекторов + встроенные сервисы. Не зависит от остального кода.
  core/         Пользователи, пространства, аккаунты, личные токены, аутентификация.
  hub/          Каталог инструментов (что видит ИИ) и исполнение вызовов. Не знает про MCP и HTTP.
  oauth/        OAuth 2.1 сервер авторизации (без привязки к фреймворку).
  mcp/          MCP-эндпоинт: на каждый запрос строит McpServer из каталога пространства.
  routes/ web/  HTTP (Hono): discovery, OAuth, вход/согласие, главная, REST API.
  db/           Схема Drizzle + миграции (папка drizzle/ в корне).
  lib/          Криптография, SSRF-безопасный fetch, rate limit, id.
```

Зависимости направлены внутрь: `routes → mcp/oauth → hub → core → connectors`. Ядро хаба
(`Hub`) используется и MCP, и REST API, и CLI, поэтому новый транспорт (например, веб-панель
с кнопкой «проверить инструмент») не требует изменений в ядре.

## Модель данных

| Таблица | Назначение |
| --- | --- |
| `users`, `workspaces`, `workspace_members` | Владелец данных — пространство. Сейчас у пользователя одно личное; команды и тарифы добавятся без миграции модели. |
| `accounts` | Подключённый аккаунт сервиса: `connector_id` + уникальное в пространстве `name` (`work`), `label`, `description` (подсказка ИИ), `config` (открытые настройки), `credentials_encrypted`, `status`, `settings.disabledActions`, `metadata.identity` (например, адрес почты). |
| `oauth_clients` | ИИ-приложения: зарегистрированные через DCR и закэшированные Client ID Metadata Documents. |
| `oauth_grants` | «Приложение X подключено к пространству Y». Отзыв гранта отзывает все его токены. |
| `oauth_authorization_codes`, `oauth_tokens` | Одноразовые коды и токены (только хэши). Refresh-токены ротируются. |
| `api_tokens` | Личные токены `ac_pat_…` для CLI, скриптов и MCP-клиентов со статическими заголовками. |
| `web_sessions` | Сессии браузера (хэш токена из cookie). |
| `oauth_apps` | Свои OAuth-приложения пользователя у провайдеров сервисов (секрет зашифрован). Приложения на весь хаб — в переменных `OAUTH_APP_*`. |
| `account_oauth` | OAuth-токены аккаунта (зашифрованы, AAD = id аккаунта), срок, scopes, каким приложением выданы. |
| `oauth_connect_states` | Незавершённые подключения аккаунтов через OAuth (хэш `state`, PKCE, 15 минут). |
| `custom_connectors` | Сервисы пространства без кода: внешние MCP-серверы (адрес, авторизация, сохранённый список инструментов) и HTTP-манифесты. |
| `tool_calls` | Аудит: кто (приложение/токен), какой инструмент, какой аккаунт, статус, длительность. Аргументы не хранятся. |

Миграции генерируются из `src/db/schema.ts` (`npm run db:generate`) и применяются при старте
под advisory-lock, так что параллельный старт нескольких инстансов безопасен. CI проверяет,
что миграции соответствуют схеме.

## Как аккаунты превращаются в инструменты

`buildCatalog()` — чистая функция от (коннекторы, аккаунты, настройки пространства):

- **grouped** (по умолчанию): один инструмент на действие сервиса, `gmail_search`, с аргументом
  `account` (enum имён аккаунтов, в описании — подписи, адреса и подсказки). Если аккаунт один,
  аргумент необязателен. Компактно: 5 аккаунтов не умножают число инструментов.
- **per_account**: `gmail_work_search`, `gmail_personal_search` — максимально явно, но
  инструментов больше.
- Всегда есть `anyconnect_list_accounts` — ИИ может спросить, что подключено.
- Выключенные аккаунты и скрытые действия (`settings.disabledActions`) в каталог не попадают.
- Имена инструментов всегда `^[a-zA-Z0-9_-]{1,64}$` (общий знаменатель Claude и OpenAI).
- Аннотации MCP (`readOnlyHint`, `destructiveHint`…) берутся из `hints` действия: по ним клиенты
  решают, спрашивать ли подтверждение.

На будущее: режим **discovery** (мета-инструменты `search_tools` / `call_tool`) для сотен
инструментов добавляется как третий вариант `buildCatalog` без изменений в коннекторах.

## Исполнение вызова

`Hub.callTool()`: выбор аккаунта → валидация входа схемой коннектора → свежая проверка, что
аккаунт включён → расшифровка ключей (AAD = id аккаунта) → запуск с таймаутом и отменой →
нормализация результата → аудит. `ConnectorError('auth')` помечает аккаунт `needs_reauth`,
неожиданные исключения превращаются в «Internal error (ref …)» без утечки деталей.

## MCP-транспорт

`createMcpHandler` из `@modelcontextprotocol/server` v2: спецификация 2026-07-28 (без сессий,
`server/discover`) и автоматический stateless-режим для клиентов 2025 года. Сервер собирается
на каждый HTTP-запрос из каталога пространства вызывающего, поэтому новый аккаунт виден при
следующем `tools/list`, а любой инстанс может обслужить любой запрос.

## OAuth

Хаб сам является сервером авторизации (SDK v2 содержит только сторону ресурса):

- Discovery: `/.well-known/oauth-protected-resource[/mcp]` (RFC 9728) и
  `/.well-known/oauth-authorization-server` (RFC 8414). 401 на `/mcp` содержит
  `WWW-Authenticate: Bearer resource_metadata="…"`.
- Регистрация клиентов: Client ID Metadata Documents (предпочтительно; Claude использует их,
  когда сервер объявляет `client_id_metadata_document_supported` и метод `none`) и DCR.
  Загрузка документов защищена от SSRF, документы кэшируются.
- Только `response_type=code` + PKCE S256. Redirect URI сравниваются точно, для loopback порт
  игнорируется (RFC 8252), как требует Claude Code.
- Токены непрозрачные (`ac_at_…`, `ac_rt_…`), в базе только SHA-256. Access — 1 час,
  refresh — 90 дней со сдвигом при ротации. Повтор старого refresh-токена позже 60 секунд после
  ротации отзывает весь грант. Повтор кода авторизации отзывает выданное по нему.
- Токены привязаны к ресурсу `https://<хаб>/mcp` (RFC 8707), REST API их не принимает
  (у них только scope `mcp`).

Интерфейс проверки токенов (`HubTokenVerifier`) отделён от сервера авторизации: при переходе
на внешний IdP (WorkOS, Auth0 и т.п.) для коммерческой версии меняется только он.

## Безопасность

- Мастер-ключ `ENCRYPTION_KEY` только в окружении; ротация через `ENCRYPTION_KEYS_PREVIOUS`.
  Из него же через HKDF выводятся ключи для других целей.
- Cookie `__Host-` (Secure, HttpOnly, SameSite=Lax), CSRF: double-submit + Origin.
- CSP без скриптов, запрет фреймов на страницах входа/согласия, `Referrer-Policy: no-referrer`.
- Rate limit на вход, токены, регистрацию (в памяти; при нескольких инстансах — вынести в
  Postgres/Redis за тем же интерфейсом).
- Периодическая очистка просроченных кодов, токенов, сессий, неиспользованных DCR-клиентов и
  старого аудита (90 дней).

## Движок коннекторов

Подробно — в `docs/CONNECTORS.md`. Коротко: весь сетевой ввод-вывод коннекторов идёт через
`ctx.fetch` и `ctx.network` (`src/lib/network.ts`, проверка адреса в момент соединения), REST-сервисы
описываются HTTP-манифестом (`src/connectors/manifest`), общий HTTP-клиент
(`src/connectors/http/client.ts`) сопоставляет ответы сервиса с ошибками хаба, а OAuth-провайдеры
лежат в отдельном реестре (`src/connectors/oauth/providers.ts`). Хаб сам является OAuth-клиентом
сервисов: `core/oauth-apps.ts` (приложения), `core/connect.ts` (подключение), `core/oauth-tokens.ts`
(хранение и обновление токенов), `core/health.ts` (фоновая проверка аккаунтов), `jobs/` (очередь
pg-boss). Сервисы пространства без кода (внешние MCP-серверы и манифесты) хранит
`core/custom-connectors.ts` и добавляет `core/custom-services.ts`; `WorkspaceConnectorResolver`
смешивает их со встроенными.

## Точки расширения на следующие этапы

| Этап | Куда встраивается |
| --- | --- |
| Почта, Telegram | Новые коннекторы в `src/connectors/builtin`. OAuth-сервисы (Gmail) подключаются через `/connect/<сервис>`, токены хранит и обновляет хаб (`ctx.oauth`). Постоянные сессии Telegram/WhatsApp — отдельный шлюз. |
| Фоновые процессы (замена задач на MacBook) | Очередь pg-boss уже есть (`src/jobs`), `npm run start:worker` — отдельный процесс задач; расписания и вебхуки пользователя добавятся как `JobDefinition` и сущности пространства. |
| Веб-панель | Работает поверх существующего REST API; формы строятся из JSON-схем `/api/v1/connectors`. |
| Любой API без кода | HTTP-манифесты пространства уже хранятся в `custom_connectors`; импорт OpenAPI станет ещё одним способом получить манифест. |
| Подключение чужих MCP-серверов | Готово: `POST /api/v1/services` с `kind: mcp`, OAuth обнаруживается и клиент регистрируется автоматически. |
| Коммерческая версия | Пространства с участниками и ролями уже в схеме; внешний IdP через `HubTokenVerifier`; лимиты — в `RateLimiter`. |

## Оформление веб-панели

Палитра «Графит и сигнал»: яркий оранжевый акцент, светлая тема на белом, тёмная на матовом
графите (не чисто чёрный). Все цвета заданы токенами в `src/web/theme.ts` (`THEMES.light`,
`THEMES.dark`), CSS собирается из них в `src/web/styles.ts`. Тема выбирается по настройке ОС;
атрибут `data-theme="light|dark"` на `<html>` переопределяет её, так что ручной переключатель
добавляется без правки палитры. Яркий `--accent` используется для заливки (кнопки) с тёмным
текстом `--accent-text`; для ссылок и текста акцентного цвета есть `--accent-ink`.
`test/theme.test.ts` проверяет контраст WCAG AA для всех пар текст/фон, поэтому новый цвет
добавляется токеном в обе темы и, если это текст, парой в `TEXT_PAIRS`.
