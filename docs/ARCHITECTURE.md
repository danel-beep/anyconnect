# Архитектура AnyConnect

Документ описывает фундамент (этап 1) и то, как в него встраиваются следующие этапы.

## Слои

```
src/
  connectors/   SDK коннекторов + встроенные сервисы. Не зависит от остального кода.
  core/         Пользователи, пространства, аккаунты, личные токены, аутентификация.
  hub/          Каталог инструментов (что видит ИИ) и исполнение вызовов. Не знает про MCP и HTTP.
  oauth/        OAuth 2.1 сервер авторизации (без привязки к фреймворку).
  mcp/          MCP-эндпоинт: на каждый запрос строит McpServer из каталога пространства.
  routes/ web/  HTTP (Hono): discovery, OAuth, вход/согласие, главная, REST API.
  db/           Схема Drizzle + миграции (папка drizzle/ в корне).
  lib/          Криптография, SSRF-безопасный fetch, rate limit, id.
```

Зависимости направлены внутрь: `routes → mcp/oauth → hub → core → connectors`. Ядро хаба
(`Hub`) используется и MCP, и REST API, и CLI, поэтому новый транспорт (например, веб-панель
с кнопкой «проверить инструмент») не требует изменений в ядре.

## Модель данных

| Таблица | Назначение |
| --- | --- |
| `users`, `workspaces`, `workspace_members` | Владелец данных — пространство. Сейчас у пользователя одно личное; команды и тарифы добавятся без миграции модели. |
| `accounts` | Подключённый аккаунт сервиса: `connector_id` + уникальное в пространстве `name` (`work`), `label`, `description` (подсказка ИИ), `config` (открытые настройки), `credentials_encrypted` (шифруется собственным ключом аккаунта), `data_key_encrypted` (этот ключ, зашифрованный мастер-ключом), `status`, `settings.disabledActions`, `metadata.identity` (например, адрес почты). |
| `oauth_clients` | ИИ-приложения: зарегистрированные через DCR и закэшированные Client ID Metadata Documents. |
| `oauth_grants` | «Приложение X подключено к пространству Y». Отзыв гранта отзывает все его токены. `ai_client_id` — каким ИИ-клиентом считается приложение, `persona_id` — к какой персоне привязан доступ. |
| `oauth_authorization_codes`, `oauth_tokens` | Одноразовые коды и токены (только хэши). Refresh-токены ротируются. |
| `api_tokens` | Личные токены `ac_pat_…` для CLI, скриптов и MCP-клиентов со статическими заголовками (тоже с `ai_client_id` и `persona_id`). |
| `ai_clients` | ИИ-клиент так, как его понимает пользователь: «Claude», «ChatGPT», «скрипт бэкапа». Правила доступа ссылаются на него, поэтому переподключение приложения их не сбрасывает. |
| `personas` | Персона («Работа», «Личное»): набор аккаунтов, потолок доступа и свой адрес MCP `/mcp/<slug>`. |
| `access_rules` | Правила доступа: кто (клиент и/или персона) × что (аккаунт, сервис или всё) → уровень доступа, подтверждение, окно отмены. |
| `pending_calls` | Вызовы, ждущие подтверждения или конца окна отмены. Аргументы и результат зашифрованы, строки удаляются через сутки. |
| `notification_channels` | Куда хаб пишет владельцу: Telegram-чат для подтверждений (привязка одноразовым кодом). |
| `web_sessions` | Сессии браузера (хэш токена из cookie), `amr` — чем подтверждён вход, `authenticated_at` — когда. |
| `pending_logins` | Вход, ожидающий второго фактора: пароль верный, сессии ещё нет (хэш токена, 5 минут). |
| `user_totp` | Секрет приложения-аутентификатора (зашифрован, AAD `user:<id>:totp`), `confirmed_at`, последний принятый шаг времени. |
| `user_recovery_codes` | Коды восстановления: только SHA-256, отметка об использовании. |
| `webauthn_credentials` | Passkey: id ключа, открытый ключ, счётчик, транспорты, признак синхронизации, название. |
| `webauthn_challenges` | Выданные WebAuthn-challenge: 5 минут, одноразовые, привязаны к браузеру. |
| `oauth_apps` | Свои OAuth-приложения пользователя у провайдеров сервисов (секрет зашифрован). Приложения на весь хаб — в переменных `OAUTH_APP_*`. |
| `account_oauth` | OAuth-токены аккаунта (зашифрованы ключом аккаунта, как и `credentials`), срок, scopes, каким приложением выданы. |
| `oauth_connect_states` | Незавершённые подключения аккаунтов через OAuth (хэш `state`, PKCE, 15 минут). |
| `custom_connectors` | Сервисы пространства без кода: внешние MCP-серверы (адрес, авторизация, сохранённый список инструментов) и HTTP-манифесты. |
| `tool_calls` | Аудит: кто (приложение/токен), какой инструмент, какой аккаунт, статус, длительность. Аргументы не хранятся. |

Миграции генерируются из `src/db/schema.ts` (`npm run db:generate`) и применяются при старте
под advisory-lock, так что параллельный старт нескольких инстансов безопасен. CI проверяет,
что миграции соответствуют схеме.

## Как аккаунты превращаются в инструменты

`buildCatalog()` — чистая функция от (коннекторы, аккаунты, настройки пространства, клиент,
статистика использования). Она собирает три группы инструментов и решает, какие из них показать
в `tools/list`.

**Инструменты сервисов.**

- **grouped** (по умолчанию): один инструмент на действие сервиса, `gmail_search`, с аргументом
  `account` (enum имён аккаунтов, в описании — подписи, адреса и подсказки). Если аккаунт один,
  аргумент необязателен. Компактно: 5 аккаунтов не умножают число инструментов.
- **per_account**: `gmail_work_search`, `gmail_personal_search` — максимально явно, но
  инструментов больше.
- У читающих инструментов с несколькими аккаунтами `account` необязателен и по умолчанию равен
  `"all"`: хаб выполняет действие на всех аккаунтах параллельно (до 8 одновременно) и сливает
  ответ. Списки становятся одним списком, каждый элемент помечен `account`, элементы берутся по
  очереди из каждого аккаунта (обрезка по размеру не выкидывает целый аккаунт), курсоры — по
  аккаунтам. Ошибка одного аккаунта попадает в `errors` и не роняет весь ответ. Пишущие
  инструменты всегда требуют один аккаунт.

**Единые инструменты** (`mail_search`, `messages_send`, `calendar_list_events`…). Если общую
операцию из `src/connectors/capabilities.ts` реализуют хотя бы два разных коннектора, появляется
один инструмент на все сервисы сразу. У списочных операций `account` — `"all"` (по умолчанию),
имя сервиса (`telegram`) или `сервис:аккаунт` (`telegram:shop`); результаты проверяются схемой
операции (лишние поля отбрасываются), сортируются (`sortBy`) и обрезаются по `limit`. Одиночные
операции (`messages_send`, `mail_read`) выполняются на одном аккаунте `сервис:аккаунт`.
Список аккаунтов с ключами есть в инструкциях сервера, поэтому описания инструментов короткие.

**Служебные инструменты** (`anyconnect_*`): `list_accounts`, `search_tools` (поиск инструмента по
описанию задачи, сразу со схемами первых трёх), `describe_tool`, `call_tool` (вызвать
неперечисленный инструмент) и `call_tools` (до 10 независимых вызовов за один шаг, параллельно;
вложенность запрещена, у каждого вызова свой `ok`).

**Что показывается в `tools/list`** (`settings.toolListing`, CLI `listing:set`):

- `direct` — всё: `list_accounts`, `call_tools`, единые инструменты и инструменты сервисов;
- `discovery` — служебные инструменты и «витрина»: сначала инструменты, которыми пространство
  пользуется чаще всего (журнал за 30 дней), затем единые списочные, пишущие и одиночные — пока
  помещаются в бюджет; остальное ИИ находит через `search_tools` и вызывает через `call_tool`;
- `auto` (по умолчанию) — `direct`, пока список укладывается в бюджет `TOOL_LIST_TOKEN_BUDGET`
  (3000 токенов) и в лимит клиента на число инструментов (Cursor — 40), иначе `discovery`.

Так контекст, который ИИ тратит на описание инструментов, не растёт с числом сервисов и
аккаунтов. Размер считается по тому, что реально уходит модели (имя, описание, схема входа).
`GET /api/v1/tools` и `npm run cli -- tools:list` показывают выбранный режим и размер списка.

**Общие правила.**

- Выключенные аккаунты и скрытые действия (`settings.disabledActions`) в каталог не попадают.
- Имена инструментов всегда `^[a-zA-Z0-9_-]{1,64}$` (общий знаменатель Claude и OpenAI).
- Аннотации MCP (`readOnlyHint`, `destructiveHint`…) берутся из `risk` и `hints` действия: по ним
  клиенты решают, спрашивать ли подтверждение.
- Фильтр `allow(connector, action, account)` (политика, персоны) применяется первым: запрещённый
  аккаунт пропадает из `account`, действие без разрешённых аккаунтов — из каталога. Поиск и
  `call_tool` работают только по отфильтрованному каталогу.
- Если действие объявило `response.fields`, у инструмента появляется аргумент `fields`.

Код: `hub/catalog.ts` (сборка), `hub/discovery.ts` (выбор режима и поиск), `hub/merge.ts`
(слияние ответов), `hub/builtin-tools.ts` (служебные инструменты).

### Оценка эффективности (`eval/`)

`npm run eval` поднимает хаб с синтетическим набором из 20 сервисов (почта, мессенджеры,
календари, трекеры, Stripe, GitHub, Ozon…) и проверяет цели:

- `tools/list` не больше 3000 токенов при 1, 3, 6, 10 и 20 сервисах;
- 20 запросов на естественном языке находят нужный инструмент в первой тройке `search_tools`;
- 8 реальных задач («найди счёт ACME во всех ящиках и отправь номер Ивану в Telegram»)
  решаются за 1–3 вызова и в режиме `auto`, и в `direct`.

Скрипт агента в `eval/harness.ts` действует так, как велят инструкции сервера: вызывает
перечисленный инструмент сразу, остальные ищет одним `search_tools`. Новая задача — запись в
`eval/tasks.ts`; eval входит в `npm run check`.

## Исполнение вызова

`Hub.callTool()` сначала разбирает вызов: выбирает аккаунт, проверяет вход схемой коннектора и
свежее состояние аккаунта. Затем единица работы «одно действие на одном аккаунте»
(`CallContext`) проходит через единый исполнитель `src/hub/executor.ts` — цепочку этапов
(middleware) в фиксированном порядке:

| Этап | Что делает | Где реализован |
| --- | --- | --- |
| `audit` | Пишет каждый вызов в `tool_calls` (статус, исход `outcome`, итоговый риск, длительность; без аргументов). Внешний, поэтому видит и отказы | `hub/stages/audit.ts` |
| `policy` | Кто что может: клиент × аккаунт × риск, персоны | `security/stages.ts` |
| `risk` | Хук действия `assessRisk` может повысить риск конкретного вызова | `hub/stages/risk.ts` |
| `confirm` | Подтверждение рискованного у пользователя (в чате, в Telegram, на странице) и окно отмены | `security/stages.ts` |
| `limits` | Лимиты сервиса на аккаунт (с коротким ожиданием слота) и повтор временных сбоев только у идемпотентных действий | `hub/stages/limits.ts` |
| `idempotency` | Не даёт случайно повторить одинаковую запись (повтор ИИ после таймаута): успешная запись запоминается на `IDEMPOTENCY_WINDOW_SECONDS`, одновременные одинаковые вызовы склеиваются | `hub/stages/idempotency.ts` |
| `untrusted` | Пометка чужого текста как данных (защита от prompt injection) | `security/stages.ts` |
| `shape` | Выбор полей, удаление пустого, бюджет размера ответа (`TOOL_RESULT_MAX_TOKENS`) | `hub/stages/shape.ts`, `hub/shaping.ts` |
| вызов | Расшифровка ключей (лениво, `call.context()`), запуск с таймаутом и отменой, нормализация | `Hub.invoke` |

Этап — функция `(call, next) => result`: может вернуть свой результат (отказ), вызвать `next()`
повторно (ретрай) или обработать результат. Новое правило — ещё один этап, ядро и коннекторы не
меняются. Этапы заменяются через `createServices({ stages })`; `executor.execute(call, { skip })`
позволяет исполнить уже одобренный вызов без повторного подтверждения. `call.locals` — общий
«карман» этапов (например, решение политики для этапа подтверждения).

Ключи расшифровываются только когда нужны (`call.context()`), поэтому отказ политики их не
трогает. `ConnectorError('auth')` помечает аккаунт `needs_reauth`, неожиданные исключения
превращаются в «Internal error (ref …)» без утечки деталей. Внутренние поля результата (`data`,
`error`) убираются перед отправкой клиенту.

Хранилище идемпотентности и лимитер сейчас в памяти процесса (одного инстанса достаточно); при
нескольких инстансах они переезжают в Postgres/Redis за теми же интерфейсами
(`IdempotencyStore`, `RateLimiter`).

Метаданные действий (`risk`, `undo`, `capability`, `response`, `rateLimit`) и общие интерфейсы
описаны в [CONNECTORS.md](CONNECTORS.md).

## MCP-транспорт

`createMcpHandler` из `@modelcontextprotocol/server` v2: спецификация 2026-07-28 (без сессий,
`server/discover`) и автоматический stateless-режим для клиентов 2025 года. Сервер собирается
на каждый HTTP-запрос из каталога пространства вызывающего, поэтому новый аккаунт виден при
следующем `tools/list`, а любой инстанс может обслужить любой запрос.

## OAuth

Хаб сам является сервером авторизации (SDK v2 содержит только сторону ресурса):

- Discovery: `/.well-known/oauth-protected-resource[/mcp]` (RFC 9728) и
  `/.well-known/oauth-authorization-server` (RFC 8414). 401 на `/mcp` содержит
  `WWW-Authenticate: Bearer resource_metadata="…"`.
- Регистрация клиентов: Client ID Metadata Documents (предпочтительно; Claude использует их,
  когда сервер объявляет `client_id_metadata_document_supported` и метод `none`) и DCR.
  Загрузка документов защищена от SSRF, документы кэшируются.
- Только `response_type=code` + PKCE S256. Redirect URI сравниваются точно, для loopback порт
  игнорируется (RFC 8252), как требует Claude Code.
- Токены непрозрачные (`ac_at_…`, `ac_rt_…`), в базе только SHA-256. Access — 1 час,
  refresh — 90 дней со сдвигом при ротации. Повтор старого refresh-токена позже 60 секунд после
  ротации отзывает весь грант. Повтор кода авторизации отзывает выданное по нему.
- Токены привязаны к ресурсу `https://<хаб>/mcp` (RFC 8707), REST API их не принимает
  (у них только scope `mcp`). У каждой персоны свой ресурс `https://<хаб>/mcp/<slug>` со своими
  метаданными (`/.well-known/oauth-protected-resource/mcp/<slug>`): токен персоны не работает на
  общем адресе, и наоборот.
- На странице согласия пользователь видит персону (если адрес персонный) и выбирает, каким
  ИИ-клиентом считать приложение: известные приложения узнаются сами (`app:claude`, адрес
  метаданных клиента), остальные можно связать с уже существующим клиентом.

Интерфейс проверки токенов (`HubTokenVerifier`) отделён от сервера авторизации: при переходе
на внешний IdP (WorkOS, Auth0 и т.п.) для коммерческой версии меняется только он.

## Безопасность

- Мастер-ключ `ENCRYPTION_KEY` только в окружении; ротация через `ENCRYPTION_KEYS_PREVIOUS`.
  Из него же через HKDF выводятся ключи для других целей.
- Cookie `__Host-` (Secure, HttpOnly, SameSite=Lax), CSRF: double-submit + Origin.
- CSP разрешает только собственные скрипты (`script-src 'self'`, `connect-src 'self'`): единственный
  скрипт — `/assets/webauthn.js` для passkey, без inline-кода. Запрет фреймов на страницах
  входа/согласия, `Referrer-Policy: no-referrer`.
- Rate limit на вход, токены, регистрацию (в памяти; при нескольких инстансах — вынести в
  Postgres/Redis за тем же интерфейсом).
- Периодическая очистка просроченных кодов, токенов, сессий, незавершённых входов,
  WebAuthn-challenge, неиспользованных DCR-клиентов и старого аудита (90 дней).

### Защита данных

**Шифрование по аккаунтам (envelope encryption).** У каждого аккаунта свой случайный ключ данных
(DEK, AES-256-GCM). Им шифруются ключи сервиса и OAuth-токены (`d1.`-конверты, AAD = id аккаунта), а сам DEK
хранится зашифрованным мастер-ключом (`account:<id>:dek`). Мастер-ключ скрыт за интерфейсом
`KeyWrapper`, поэтому позже его можно перенести в KMS/HSM, не трогая данные. Старые записи,
зашифрованные мастер-ключом напрямую (`v1.`), читаются и переводятся на DEK при старте; при
ротации `ENCRYPTION_KEY` перешифровываются только DEK (`npm run cli -- keys:rotate`).

**ИИ-клиенты, правила и персоны.** Каждый OAuth-грант и личный токен связан с ИИ-клиентом.
Политика (`security/policy.ts`, чистая функция) решает для пары «вызывающий × аккаунт» уровень
доступа (`none` / `read` / `write` / `full`), когда спрашивать подтверждение
(`never` / `dangerous` / `write` / `always`) и окно отмены. По каждому полю побеждает самое точное
правило: аккаунт точнее сервиса, сервис точнее «всего», правило для клиента и персоны точнее
правила для одного из них; при равенстве — более строгое. Умолчания пространства: полный
доступ, подтверждать опасное, без окна отмены (`PATCH /api/v1/security`). Персона ограничивает
список аккаунтов и потолок доступа. Политика применяется дважды: при сборке каталога (ИИ не
видит запрещённого, в том числе в `list_accounts` и инструкциях) и на каждом вызове (этап
`policy`, затем ещё раз в `confirm` с итоговым риском после `assessRisk`).

**Подтверждения.** Если вызов требует подтверждения, хаб сохраняет его в `pending_calls` и
спрашивает пользователя:

1. в самом чате — MCP elicitation через multi round-trip (клиенты спецификации 2026-07-28,
   объявившие `elicitation`). Состояние вопроса подписано HMAC и привязано к вызову, клиенту и
   аргументам: подделать ответ или перенести его на другой вызов нельзя;
2. иначе (сегодняшние Claude и ChatGPT без elicitation) — кнопками в Telegram-боте хаба и на
   странице `/confirm/<id>`. Вызов ждёт ответа до `CONFIRMATION_WAIT_SECONDS`, затем ИИ получает
   «ждёт подтверждения» со ссылкой. Повтор того же вызова с теми же аргументами возвращает
   статус или результат, а не новый вопрос; после выдачи результата следующий такой же вызов —
   уже новое действие.

Одобренный вне чата вызов исполняет `PendingCallRunner` (на каждом инстансе, захват строк
`FOR UPDATE SKIP LOCKED`, поэтому ровно один раз) от имени исходного вызывающего и через ту же
цепочку этапов: если доступ за это время отозвали, вызов будет отклонён. Одобрить или отклонить
может только сам пользователь (страница в браузере или его Telegram-чат); токены, даже личные,
могут лишь отменить. Неотвеченные подтверждения истекают (`CONFIRMATION_TTL_MINUTES`).

**Окно отмены.** Правило может задать `undoWindowSeconds`, действие — `undo: { kind: 'delay' }`:
одобренный вызов ждёт указанное время, и его можно отменить в Telegram, на странице или через
`POST /api/v1/pending-calls/<id>/cancel`.

**Telegram-бот.** Собственный бот хаба (`TELEGRAM_BOT_TOKEN`, не коннектор). Привязка: кнопка на
странице «Подтверждения» даёт ссылку `t.me/<бот>?start=<одноразовый код>`. Webhook
`/telegram/webhook` принимает обновления только с секретом, выведенным из мастер-ключа; нажатия
принимаются только из чата владельца вызова.

**Недоверенный контент.** Результаты действий, которые читают внешний мир (письма, сообщения,
страницы; всё, кроме `hints.openWorld: false`), оборачиваются в
`⟦untrusted <случайный id> source="…"⟧ … ⟦/untrusted <id>⟧`, а инструкции хаба велят модели
считать такой текст данными. Случайный id не даёт тексту внутри «закрыть» блок.

**Цепочка поставки.** Dependabot (npm, Actions, Docker), CodeQL, gitleaks по всей истории,
`npm audit` и проверка подписей пакетов в CI; у workflow минимальные права.

### Вход и второй фактор

Вторые факторы — **приложение-аутентификатор** (TOTP) и **passkey** (WebAuthn); к ним
прилагаются 10 одноразовых **кодов восстановления**. Настраиваются на странице `/security`.

```
пароль ──► есть второй фактор? ── нет ──► сессия amr=[pwd]
                │ да
                ▼
     pending_login (cookie __Host-ac_mfa, 5 мин) ──► /login/verify
                │ код TOTP / код восстановления / passkey
                ▼
     сессия amr=[pwd,otp] | [pwd,rec] | [pwd,hwk]

кнопка «Войти с passkey» (discoverable credential + проверка пользователя) ──► сессия amr=[hwk]
```

- **TOTP** (RFC 6238: SHA-1, 6 цифр, 30 секунд, допуск ±1 шаг) реализован на `node:crypto`
  (`src/lib/totp.ts`). Секрет шифруется `SecretBox` (AAD `user:<id>:totp`). Фактор включается
  только после ввода верного кода; принятый шаг времени запоминается, повтор того же или более
  старого кода отклоняется (условный `UPDATE`, так что гонка двух запросов тоже не проходит).
  QR-код рисуется на сервере как SVG (`uqr`), рядом — ключ текстом и ссылка `otpauth://`.
- **Коды восстановления**: 10 кодов по 80 бит (`XXXX-XXXX-XXXX-XXXX`), показываются один раз,
  в базе — SHA-256 от `<id пользователя>:<код>`. Создаются при включении TOTP, можно
  перевыпустить. Удаляются вместе с последним фактором: сами по себе фактором не являются.
- **Passkey** через `@simplewebauthn/server`: RP ID — хост из `PUBLIC_URL`, ожидаемый origin —
  `PUBLIC_URL` (поэтому passkey привязаны к домену: при смене домена их нужно добавить заново).
  Challenge хранятся в `webauthn_challenges`, живут 5 минут, удаляются при использовании
  (`DELETE … RETURNING`) и привязаны к CSRF-cookie браузера, в котором выданы. Счётчик подписей
  и признак синхронизации обновляются при каждом входе. Браузерная часть — рукописный
  `src/web/webauthn-client.ts` без сборщика: формы с `data-passkey` скрыты, пока скрипт не
  убедится, что браузер поддерживает passkey, поэтому без JS остаются пароль и коды.
- **Ограничение попыток**: коды второго фактора — 5 за 5 минут на пользователя и 30 за
  15 минут на IP; WebAuthn-запросы — 30 за 5 минут на IP (тот же `RateLimiter`).
- **`amr` сессии** (значения RFC 8176: `pwd`, `otp`, `hwk`, плюс `rec` для кода
  восстановления) и `authenticated_at` позволяют будущим функциям требовать сильный вход
  (`isStrongAuth`) или недавний вход (`isRecentAuth`) — см. `src/core/auth-methods.ts`.
  Подтверждение нового фактора внутри сессии дописывает его в `amr`.
- **Step-up**: изменения на `/security` (TOTP, passkey, коды) требуют входа не старше
  10 минут; иначе — `/login?reauth=1`, обычный вход заново (с паролем и вторым фактором или
  passkey), который заменяет сессию.
- **`REQUIRE_2FA=true`**: пользователь без второго фактора с главной, REST API (по cookie) и
  экрана согласия OAuth отправляется на `/security?next=…`; если фактор есть, а сессия создана
  без него, — на повторный вход. Проверка — `secondFactorRedirect` в `src/routes/context.ts`.
- **Потеря устройства**: `npm run cli -- users:2fa:reset --email <почта>` удаляет TOTP,
  passkey и коды восстановления пользователя; дальше вход только по паролю.

Слои: правила факторов — в `src/core` (`totp.ts`, `recovery-codes.ts`, `passkeys.ts`,
фасад `second-factors.ts`), состояние браузера (сессии, незавершённые входы) — в `src/web`,
HTTP — `src/routes/login.tsx` и `src/routes/security.tsx`.

## Движок коннекторов

Подробно — в `docs/CONNECTORS.md`. Коротко: весь сетевой ввод-вывод коннекторов идёт через
`ctx.fetch` и `ctx.network` (`src/lib/network.ts`, проверка адреса в момент соединения), REST-сервисы
описываются HTTP-манифестом (`src/connectors/manifest`), общий HTTP-клиент
(`src/connectors/http/client.ts`) сопоставляет ответы сервиса с ошибками хаба, а OAuth-провайдеры
лежат в отдельном реестре (`src/connectors/oauth/providers.ts`). Хаб сам является OAuth-клиентом
сервисов: `core/oauth-apps.ts` (приложения), `core/connect.ts` (подключение), `core/oauth-tokens.ts`
(хранение и обновление токенов), `core/health.ts` (фоновая проверка аккаунтов), `jobs/` (очередь
pg-boss). Сервисы пространства без кода (внешние MCP-серверы и манифесты) хранит
`core/custom-connectors.ts` и добавляет `core/custom-services.ts`; `WorkspaceConnectorResolver`
смешивает их со встроенными.

## Точки расширения на следующие этапы

| Этап | Куда встраивается |
| --- | --- |
| Почта, Telegram | Новые коннекторы в `src/connectors/builtin`. OAuth-сервисы (Gmail) подключаются через `/connect/<сервис>`, токены хранит и обновляет хаб (`ctx.oauth`). Постоянные сессии Telegram/WhatsApp — отдельный шлюз. |
| Фоновые процессы (замена задач на MacBook) | Очередь pg-boss уже есть (`src/jobs`), `npm run start:worker` — отдельный процесс задач; расписания и вебхуки пользователя добавятся как `JobDefinition` и сущности пространства. |
| Веб-панель | Работает поверх существующего REST API; формы строятся из JSON-схем `/api/v1/connectors`. |
| Любой API без кода | HTTP-манифесты пространства уже хранятся в `custom_connectors`; импорт OpenAPI станет ещё одним способом получить манифест. |
| Подключение чужих MCP-серверов | Готово: `POST /api/v1/services` с `kind: mcp`, OAuth обнаруживается и клиент регистрируется автоматически. |
| Коммерческая версия | Пространства с участниками и ролями уже в схеме; внешний IdP через `HubTokenVerifier`; лимиты — в `RateLimiter`. |

## Оформление веб-панели

Палитра «Графит и сигнал»: яркий оранжевый акцент, светлая тема на белом, тёмная на матовом
графите (не чисто чёрный). Все цвета заданы токенами в `src/web/theme.ts` (`THEMES.light`,
`THEMES.dark`), CSS собирается из них в `src/web/styles.ts`. Тема выбирается по настройке ОС;
атрибут `data-theme="light|dark"` на `<html>` переопределяет её, так что ручной переключатель
добавляется без правки палитры. Яркий `--accent` используется для заливки (кнопки) с тёмным
текстом `--accent-text`; для ссылок и текста акцентного цвета есть `--accent-ink`.
`test/theme.test.ts` проверяет контраст WCAG AA для всех пар текст/фон, поэтому новый цвет
добавляется токеном в обе темы и, если это текст, парой в `TEXT_PAIRS`.
