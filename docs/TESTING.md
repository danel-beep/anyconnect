# Тесты Manyplug

`npm test` запускает все тесты (Vitest, нужен Postgres из `TEST_DATABASE_URL`). CI гоняет их на
каждый PR вместе с lint, типами, сборкой и проверкой миграций.

**Файлы идут параллельно.** Каждый процесс-исполнитель Vitest (не больше 8, на машине с N ядрами —
N−1) работает со своей базой рядом с `TEST_DATABASE_URL`: `manyplug_test_w1`, `manyplug_test_w2`…
Перед прогоном `test/setup/global.ts` один раз создаёт недостающие базы, а
`test/setup/worker-database.ts` до загрузки `test/helpers.ts` направляет каждый процесс в его базу.
Сама база из `TEST_DATABASE_URL` не используется и может не существовать. Поэтому `resetDatabase()`
в одном файле не мешает файлам в других процессах; `test/test-isolation.test.ts` следит, чтобы так и
оставалось. `npm run test:visual` работает в своих базах (`manyplug_test_visual_w1`), так что его
можно запускать одновременно с `npm test`. Полный прогон — 2–2,5 минуты на 4 ядрах вместо 5,5 при последовательном запуске.

- Роли нужно право `CREATEDB` (или создайте базы `_w1`…`_wN` заранее). Если сервер отказал
  (нет права, неверный пароль), setup один раз пишет причину, а тесты без базы всё равно проходят.
- Тест, которому нужна ещё одна база, берёт её имя от своей (`ensureTestDatabase('upstream')` →
  `manyplug_test_w1_upstream`; имена и кавычки — в `test/setup/databases.ts`), а не задаёт
  фиксированное. Так же с портами: только `port: 0` или `freePort()` из `test/helpers.ts`, никаких
  постоянных портов и других общих для машины ресурсов.
- Базы исполнителей остаются между прогонами (так быстрее). Удалить их:
  `psql -Atc "select 'drop database ' || quote_ident(datname) || ';' from pg_database where datname ~ '^manyplug_test_(visual_)?w[0-9]'" | psql`.
- Отладить файлы по одному: `npx vitest run --no-file-parallelism <файлы>`.

**Быстрая проверка во время работы:** `npm run check:fast` — lint, типы и только те тесты, которые
затрагивают изменения относительно `origin/main` (по графу импортов). Файлы, которые код читает с
диска во время работы, в этот граф не попадают: изменение миграций (`drizzle/`), `package.json`,
конфигурации Vitest или `test/setup/` запускает все тесты. Перед PR — полный `npm run check`.

**Визуальная проверка одной правки.** Полный `npm run test:visual` проходит все страницы во всех
вариантах и сохраняет сотни скриншотов. Чтобы проверить свою правку и посмотреть глазами только то,
что поменялось:

```sh
# до правки: снимки нужных страниц
VISUAL_PAGES='^/app/services$' VISUAL_SCREENSHOTS=/tmp/vis-before npm run test:visual -- pages
# после правки: остаются только снимки, которые отличаются от «до»; список — в changed.txt
VISUAL_PAGES='^/app/services$' VISUAL_BASELINE=/tmp/vis-before VISUAL_SCREENSHOTS=/tmp/vis-after npm run test:visual -- pages
```

`VISUAL_PAGES` — регулярное выражение по пути страницы (обход ссылок всё равно находит все страницы,
проверяются только совпавшие; если не совпала ни одна, тест падает). `-- pages` запускает только
`pages.visual.ts`, без проверки живых обновлений. `VISUAL_BASELINE` сравнивает снимки попиксельно с
небольшим допуском (Chromium сглаживает края чуть по-разному от прогона к прогону), а случайный порт
тестового хаба на снимках заменён на `manyplug.test`, так что неизменная страница не попадает в
`changed.txt`; одна изменённая буква на странице попадает. Правила вёрстки (`layout-checks.ts`)
проверяются во всех вариантах как обычно, а полный прогон без фильтра делает CI.

**Доступность (a11y).** В том же прогоне каждая страница проверяется на доступность
(`test/visual/a11y-checks.ts`): axe-core по правилам WCAG 2.2 A/AA и best practices (контраст,
подписи у кнопок, ссылок и полей, `alt`, порядок заголовков, ориентиры `header`/`main`/`footer`, ARIA,
автообновление страницы) и собственное правило `focus-visible`: каждая ссылка, кнопка и поле, получив
фокус с клавиатуры, должны заметно измениться — сами или их обёртка (плитка с `:focus-within`).
Контраст зависит от темы, остальное от разметки, поэтому a11y проверяется в светлой и тёмной теме на
десктопе по-английски (шаблоны RU/EN общие). Правило отключается только в `a11y-checks.ts` с
причиной, не для отдельной страницы. Частые исправления: текст на оранжевой заливке — цвет
`--accent-text`, не белый; приглушённый текст — `--muted` без `opacity`; уровень заголовка на единицу
ниже родительского (у `PlanCard`/`PlansGrid` есть `heading`); страница, которая обновляется сама, —
`data-poll` на блоке, а не `<meta http-equiv=refresh>`.

| Где | Что проверяет |
| --- | --- |
| `test/*.test.ts` | Модули и сценарии одной части: каталог, исполнитель, политика, OAuth-сервер, сайт, оплата… |
| `test/connectors/` | Контракты встроенных коннекторов на записанных ответах API (`harness.ts`, без хаба и базы). |
| `test/e2e/` | Сквозные сценарии подключения: от ИИ-клиента до сервиса и обратно (ниже). |
| `test/ui-contract.test.ts` | Контракт вёрстки без браузера: классы без стилей и атрибуты `style` в `src/**/*.tsx` ([UI.md](UI.md)). |
| `eval/` | Эффективность для ИИ: размер списка инструментов, поиск, задачи за 1–3 вызова. |

**Покрытие.** Отчёт о покрытии не входит в CI (зависимость не установлена, чтобы не тянуть её в
каждый прогон). Снять его разово:
`npm i --no-save @vitest/coverage-v8@<версия vitest> && npx vitest run --coverage --coverage.include='src/**'`.
На 11.11.2026: строки 87,6%, ветки 72,3%. Без тестов остаются в основном точки входа процессов
(`src/index.ts`, `src/worker.ts`, `src/gateway/index.ts`, `src/cli/`). Изоляция данных между
рабочими пространствами проверяется на каждом маршруте с id: тот же запрос с токеном чужого
пространства должен получить 404 (`test/api-security.test.ts`, `test/security.e2e.test.ts`).
Кроме списка известных мест есть обход всех маршрутов (`test/tenant-isolation.e2e.test.ts`): тест
берёт у приложения полный список маршрутов, в каждый путь с параметром подставляет id всего, что
принадлежит другому пользователю (аккаунт, токен, профиль, ИИ-приложение, триггер, пространство),
и вызывает его от чужого имени из браузера и с API-токеном. В ответах не должно быть ничего
чужого, а чужие строки в базе не должны измениться. Новый маршрут попадает под проверку сам.

**Сбои инфраструктуры.** `test/fault-proxy.ts` — TCP-прокси перед Postgres: `cut()` рвёт все
соединения и не пускает новые (перезапуск базы), `freeze()` оставляет их открытыми, но без ответа
(разрыв сети), `restore()` пускает снова. Хаб поднимается через него
(`startTestHub({ databaseUrl: proxy.url(TEST_DATABASE_URL) })`), см. `test/outage.e2e.test.ts` и
docs/OPERATIONS.md («Сбой базы данных»).

`test/helpers.ts`: `startTestHub()` поднимает настоящий хаб на случайном порту, `TestBrowser` —
браузер с cookie, формами и `walk()` (идёт по редиректам, в том числе на сайты провайдеров).

## Сквозные тесты (`test/e2e/`)

Работает весь продакшен-код: официальный MCP-клиент, OAuth-сервер хаба и экран согласия, вход
через Google, OAuth-подключение сервиса, коннекторы, этапы исполнителя (политика, подтверждение,
пометка чужого текста). Подделан только интернет.

| Файл | Сценарий |
| --- | --- |
| `first-connection.e2e.test.ts` | Новый пользователь: Claude добавляет хаб → регистрация через Google в окне входа → согласие → два ящика Gmail из чата → поиск → письмо ждёт подтверждения → токен Google истёк (обновляется сам) → доступ отозван в Google (ИИ получает ссылку на переподключение). |
| `ai-clients.e2e.test.ts` | Каждый клиент из `AI_CLIENTS`: вход по OAuth так, как это делает клиент, экран согласия (имя, «известное приложение», предупреждения), список инструментов, вызов сервиса, подтверждение (в чате или по ссылке), обновление токена, отключение в кабинете, повторное подключение с теми же правилами. |
| `confirmation-rules.e2e.test.ts` | Таблица правил подтверждения: пользователь меняет их на странице «Правила», ИИ вызывает чтение, запись и опасное действие Gmail; итог — выполнено, спросили, окно отмены или инструмента нет. Для клиента со спросом в чате и для клиента со ссылкой. |
| `connection-edge-cases.e2e.test.ts` | Адрес со слэшем на конце, адрес персоны, отказ на экране согласия, отмена входа в Google, закрытая регистрация, обязательный второй фактор посреди подключения, выход через `/oauth/revoke`. |
| `custom-service.e2e.test.ts` | Сервис без MCP: ИИ добавляет HTTP-манифест (после подтверждения пользователя), ключ вводится на странице хаба, ИИ ищет, создаёт и удаляет записи по тем же правилам. |

### Из чего собраны

- **`fake-internet.ts`** — `FakeInternet`: отвечает за настоящие адреса сервисов
  (`gmail.googleapis.com`, `claude.ai`…) и записывает каждый запрос. Подключается туда же, где у
  хаба сеть: `startTestHub({ internet })` → `createServices({ network, fetchDocument })`. Запрос к
  адресу, который никто не обслуживает, падает как недоступный хост и попадает в `unrouted`.
- **`fakes/`** — поддельные сервисы. `google.ts`: вход и согласие Google (одобряет как
  `signedIn`), OAuth с одноразовыми кодами, PKCE, секретом клиента, `refresh_token`, отзывом;
  Gmail API (профиль, поиск, письма, отправка, черновики). `crm.ts`: REST API с ключом в заголовке
  и его манифест.
- **`ai-clients.ts`** — профили ИИ-клиентов (`AI_CLIENTS`): как клиент представляется (документ
  метаданных или регистрация), какой redirect URI, какой протокол MCP, умеет ли спрашивать в чате,
  какой `_meta` шлёт, как его должен назвать хаб и что показать на экране согласия.
  `SimulatedAiClient` — клиент на официальном MCP SDK с этим профилем.
- **`journey.ts`** — шаги человека в браузере: вход через Google, кнопка «Разрешить», решение на
  странице подтверждения, данные ящиков.

### Как расширять

- **Новый ИИ-клиент** — запись в `AI_CLIENTS`. Все сквозные тесты и `oauth-client-compat.test.ts`
  подхватят её сами. Форму регистрации берите из опубликованных документов клиента.
- **Новое правило подтверждения** — строка в `ROWS` в `confirmation-rules.e2e.test.ts`.
- **Новый поддельный сервис** — класс в `fakes/` с методом `install(internet)`, который вешает
  Hono-приложение на хост сервиса (`internet.serve('api.example.com', app.fetch)`). Если сервису
  нужен OAuth, поддельный сервер авторизации ставится так же (см. `FakeGoogle`).
- Ошибку, которую находит сквозной тест, исправляйте в коде хаба, а не обходите в тесте.
