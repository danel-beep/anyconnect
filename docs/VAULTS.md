# Сейфы пользователей и запечатанные аккаунты

Цель: у оператора хаба нет прямого доступа к данным пользователей. Копия базы, бэкап, переменные
Render (`ENCRYPTION_KEY`) или взломанный админский аккаунт не должны открывать ни одного токена.

## Схема ключей

- У каждого аккаунта свой ключ данных (DEK, `src/core/account-keys.ts`). В обычном аккаунте он завёрнут
  мастер-ключом `ENCRYPTION_KEY`. В запечатанном аккаунте DEK запечатан на **публичный ключ сейфа**
  владельца (`s1.`-конверт, ECIES: X25519 + HKDF-SHA256 + AES-256-GCM, AAD = контекст аккаунта).
- Сейф (`src/lib/vault.ts`) — пара ключей X25519 на пользователя. Публичный ключ лежит в `user_vaults`.
  Приватный ключ хранится **только** завёрнутым в `vault_wraps`, под секретами, которых у хаба нет:
  - `device` — ключ устройства: 32 случайных байта в cookie `mp_vault` этого браузера (`__Host-`,
    400 дней, переживает выход и новый вход). В базе нет ни ключа, ни его хеша;
  - `oauth` — access- и refresh-токены ИИ-приложения (в базе только их SHA-256), `oauth_code` — код
    авторизации на время обмена;
  - `api_token` — личный токен (PAT);
  - `recovery` — необязательный ключ восстановления (256 бит, показывается один раз);
  - `passkey` — зарезервировано для выхода PRF ключа доступа (следующий шаг).
- Контекст завёртки `vault:<userId>:<kind>:<ref>` и сверка с публичным ключом не дают перенести
  завёртку в чужую строку.
- `UnlockedVault` реализует `KeyWrapper`, поэтому запечатанный DEK открывается тем же кодом, что и обычный.

У `VaultService` (`src/core/vaults.ts`) нарочно нет метода, который открывает сейф по одному id
пользователя: каждый путь требует секрет из запроса.

## Защищено по умолчанию

От пользователя ничего не требуется:

1. **Первый вход в браузере** (`src/routes/web-vault.ts`): если сейфа ещё нет, он создаётся, а браузер
   получает ключ устройства. С этого момента новые личные аккаунты запечатываются.
2. **ИИ-приложение**: экран согласия в браузере, где сейф открыт, заворачивает сейф под код авторизации;
   обмен кода переносит завёртку на выданные access/refresh-токены; каждый refresh переносит её снова;
   отзыв приложения удаляет завёртки (`src/core/vault-links.ts`).
3. **Личный токен**, созданный в браузере с открытым сейфом, получает свою завёртку.
4. **Новый браузер** (вход после создания сейфа) получает свой ключ устройства и запрос в
   `vault_device_requests` (только публичная половина ключа устройства). В разделе «Безопасность» он
   показывает код из 6 цифр; браузер, где сейф открыт, видит баннер «Браузер просит открыть…» и
   нажимает **Разрешить** рядом с тем же кодом. Одобрение запечатывает приватный ключ сейфа на
   публичный ключ нового устройства (`s1.`-завёртка kind `device`): одобряющий запрос не узнаёт
   секрет нового браузера, а сервер не хранит его. Запрос живёт 7 дней, потом его можно повторить.
   Закрытый браузер одобрять не может: у него нечем открыть сейф.
5. **Ключ восстановления** (по желанию): создаётся в открытом браузере, открывает сейф в любом новом
   браузере, если других не осталось.

Пока сейф закрыт в браузере, там видны список аккаунтов и журнал и можно подключать новые аккаунты
(для запечатывания нужен только публичный ключ); не открываются только сами запечатанные аккаунты.
Новый OAuth-аккаунт сохраняет токены свежим ключом аккаунта в той же транзакции, что и сам аккаунт
(`AccountService.create(..., { secrets })`), поэтому подключение работает и в закрытом браузере.
Переподключить уже запечатанный аккаунт там нельзя (нужен его ключ): ссылка отвечает 423 ещё до
перехода к сервису.
Если человек потерял все браузеры и ИИ-приложения и не создал ключ восстановления, сейф открыть нечем:
аккаунты подключаются заново. Данные в самих сервисах не теряются ни в каком случае.

## Где сейф открыт

Сейф открывается только внутри запроса, который принёс секрет (`src/core/vault-scope.ts`,
`AsyncLocalStorage`): MCP и REST по bearer-токену (`src/routes/mcp.ts`, `src/routes/api.ts`), веб-панель
по ключу устройства. Вне запроса (фоновые задачи, шлюз, админка) сейфа нет по построению, а не по
проверке, которую можно забыть. Доступ к закрытому аккаунту даёт ошибку `vault_locked` (HTTP 423) и
никогда не помечает аккаунт как сломанный. Даже `VaultLockedError`, пропущенная по пути, превращается
обработчиком ошибок (`src/app.tsx`) в 423 с понятным текстом, а не в 500.

- **Фоновые задачи** (`AccountHealthService`, обновление OAuth-токенов по расписанию) пропускают
  запечатанные аккаунты (`notSealedAccount()`): их токены обновляются при ближайшем вызове.
  Ограничение: если сервис отзывает refresh-токен после долгого простоя (Microsoft — 90 дней), такой
  аккаунт без вызовов придётся переподключить.
- **Отложенные действия** (подтверждение, окно отмены): когда вызов задерживается в запросе
  ИИ-приложения, открытый сейф держится **только в памяти процесса** под id отложенного вызова до его
  выполнения или истечения (`VaultScopes.hold` / `runHeld`, `retainVault` в `services.ts`); одобрение
  в веб-панели с открытым сейфом тоже кладёт его в память. После перезапуска сервера (или на другом
  экземпляре) вызов найдёт сейф закрытым и ответит ошибкой — пользователь повторяет запрос.
- **Удаление аккаунта** из закрытого браузера удаляет его без отзыва доступа у сервиса.
- **Командные аккаунты** пока остаются на мастер-ключе (этап 3), **мессенджеры** — тоже (этап 4):
  сессии в шлюзе работают круглосуточно.

## Что это защищает и что нет

Защищает от кражи базы, бэкапов, переменных окружения и от входа в админку: без ключа устройства,
токена ИИ-приложения или ключа восстановления ключи не расшифровать.

Не защищает от изменённого кода, выложенного на сервер: он может запомнить ключ в момент настоящего
вызова. Это закрывается доступом к GitHub и Render (аппаратный ключ, защищённая ветка `main`,
подписанные сборки), а после запуска — анклавом с аттестацией.

## Этапы

1. **Готово:** крипто-ядро, таблицы `user_vaults` / `vault_wraps`, `VaultService`, тесты.
2. **Готово:** сейф по умолчанию при первом входе, запечатывание новых личных аккаунтов, завёртки для
   ИИ-приложений и PAT, одобрение новых браузеров, ключ восстановления, отложенные действия
   (`test/vault-sealing.e2e.test.ts`).
3. Перевод существующих аккаунтов (перезапечатывание DEK на публичный ключ, удаление копии под
   мастер-ключом — необратимо, только с согласия владельца), командные аккаунты (DEK запечатан на
   сейф каждого участника), passkey PRF как ещё один способ открыть сейф.
4. Мессенджеры: входящие шифруются на публичный ключ; сессия личного Telegram в шлюзе помечается
   «всегда онлайн». Тексты на сайте и в Privacy.
